# 命令行与本地化经验

## 1. 解析器自研，不依赖预览版 API

项目用自研 `CommandLineHandler` 替代早期的 `System.CommandLine`，理由是预览 API 变更会影响发布。
动词 `compress` / `extract` / `gui` 在解析前规范化为旧式 `--compress` / `--decompress` 开关，
保证老脚本不用改；错误文案走本地化资源，不硬编码中文。

## 2. 语言要在「完整解析成功后立刻」同步

`Program.Main` 解析成功后马上设置 `LocalizationService.CurrentLanguage`，
这样无界面运行期的服务层消息（开始、成功、跳过、缺卷）才和命令行输出同语言。
只改帮助文本、不改服务层，会出现英文提示夹中文消息的混排。
`--help` 不走完整解析，所以用预扫描 `DetectLanguage(args)` 提前决定帮助语言。

## 3. 语言值先归一再使用

`zh / zh-CN / zh-Hans → zh-CN`、`zh-TW / zh-Hant / tw → zh-TW`、`en-US → en`、`ja-JP → ja`、`de-DE → de`；
未知值报参数错误（退出码 2）。当前支持简体中文、繁體中文、English、日本語、Deutsch 五种。

## 4. 纯语言参数应该平滑启动图形界面

`--lang en` 不带模式动词、不带任何批处理意图时，按指定语言启动桌面程序；
但只要带了 `--input` / `--source` / `--output` / `--text-file` 等批处理意图，仍要求显式模式动词，
避免拼错的参数被「悄悄启动界面」掩盖。

## 5. 结构化输出要主动排除敏感内容

`--output-format json` 输出 NDJSON（每行一个 JSON 事件）时，人类可读提示改写 stderr，
stdout 只承载事件流；**含密码的命令行整条排除**，不进入事件。
退出码映射在这种模式下保持不变（0/1/2/130）。
**当前实测核实**：真实压缩的 json 模式在 stdout 产生 3 行事件
（`progress` / `item` / `summary`），`Found`、`Completed`、`Log file` 走 stderr，
且 stdout 搜不到 `--password-file` 里的明文密码。

**容易踩的边界（实测发现，历史文档未写）**：`--dry-run` 会提前返回，
不走结构化输出器——即使加了 `--output-format json`，stdout 也是**空的**，
DRY-RUN 清单写在 stderr。自动化脚本若依赖 NDJSON，不能拿试运行模式来联调。

## 6. 帮助文本的折行要考虑东亚宽字符

中文、日文字符在终端占 2 列，按字节或按字符数折行都会错位。
做法是：ASCII 按单词边界切分、东亚按单字切分、保持缩进并在长缩进时动态收缩；
输出被重定向到文件时保留原样，不做宽度折叠。

## 7. 退出码是脚本契约，不要随意改

| 码 | 含义 |
| --- | --- |
| 0 | 成功（含 `--help` / `--version` / `--dry-run` 正常结束） |
| 1 | 任务失败，或找不到可用归档引擎 |
| 2 | 参数错误、密码读取失败、来源路径校验失败 |
| 130 | Ctrl+C 协作式取消（2026-11-05 实测：返回 130、日志记录取消、无残留 7zz 进程） |

`--dry-run` 只列任务，明确不创建输出目录、不写归档，可用于预检清单。
自动化测取消时注意非交互 shell 后台作业会忽略 SIGINT，详见 [04-进程与并发](04-进程与并发.md)。

## 词条外置到 JSON 后必须先处理的两个坑

**2026-11-16 批次 24（P4 路线）实测**：把五套 `Create*()` 字典迁到
`Localization/Resources/*.json` 后踩到两个问题。

1. **窗口标题会被测试程序集版本污染**：内置字典里 `WindowTitle` 是
   「基础标题 + `WithVersion()`」，导出工具在测试程序集里运行，读到的是测试工程的
   `v1.0.0`。正确做法是**资源只存基础标题**，加载后由语言服务统一拼运行版本，
   并让拼接函数**幂等**（先剥掉已有版本后缀再拼）。
2. **资源必须同时嵌入主工程与测试工程**：测试工程是链接源码编译的，
   如果只给主 csproj 加 `EmbeddedResource`，测试里加载不到资源会**静默回退默认中文**，
   表现为「英文/德语不含中文」这类测试失败，而不是编译错误。

配套守护测试：五份 JSON 键集合互相一致、与 `LanguageStrings` 属性集合一致、
每个值非空、资源标题不含测试版本、`HasResource` 对五种语言都为 true。

## 结果报告：收集存标记、写出再翻译（2026-11-16，0.8.9）

- 报告收集器跑在进度回调里，界面语言可能在收集之后才设置。收集时就写死中文标签，
  `--lang en` 会导出「中文表头 + 英文消息」的混排。改为收集器中只存语言无关标记
  （结果、操作类型、脱敏占位），写出时才按当前语言翻译，语言切换时序就不再是问题。
- 表头、标题、状态、汇总句、省略说明、脱敏说明必须全部进词条。界面本地化扫描默认只覆盖
  `Views/` 与 `App`，服务层的中文硬编码逃过扫描，要靠「键集合一致性 + 报告输出语言」测试守护。
- CSV 单元格还要防公式注入：来源名是用户数据，以 `=`、`+`、`-`、`@` 开头时要中和，
  否则用表格软件打开报告会被当公式求值。
- `--report` 这类附加产物必须放在统一收尾位置（`finally`）。只写在正常结束路径时，取消、
  异常、试运行、诊断导出等提前返回会静默不产出文件；且写失败只能告警，不能改变批次退出码。
- 界面侧创建收集器后必须设置操作类型，否则解压批次会沿用默认的「压缩」。

## 双入口一致性：命令行这边还有四条没对齐（2026-11-16 整体分析）

- **来源校验口径不同**：命令行在执行前用原始路径逐个检查，只要有一个不存在就整批以参数错误码退出；
  界面与服务层的来源收集口径是「不做存在性过滤，缺失项记一条『未找到』，其余照常处理」。
  同一份清单在两边结果不同。更细的一层：路径规范化函数是在校验**之后**才执行的，
  所以「真实文件但路径末尾带斜杠」这个已修过的缺陷在命令行又回来了；校验前必须先规范化。
  改成逐项计数会改变命令行「快速失败」契约，五语言帮助与试运行输出要同步改。
- **运行器自己的终端文案没本地化**：「命令行不构造界面、语言恒为简体中文」的根因已修好
  （启动时会同步 `--lang`，服务层消息也走本地化资源），但命令行批处理执行器里几十处终端文案
  仍是硬编码英文，另有两处硬编码中文。实测 `--lang en` 跑不存在的输入，错误仍是中文。
  历史文档里「CLI 语言恒为中文」这条结论已过时，照旧结论去修会做重复工作。
- **纯 `--lang` 启动会被系统语言覆盖**：五份帮助都写了「单独使用 `--lang` 时直接以该语言启动界面」，
  启动流程也确实先设好了语言，但界面状态类构造时又无条件做一次系统语言检测把它盖掉。
  当系统语言恰好是简体中文时，给选中项赋同值不会触发属性变化通知，还会出现
  「界面是命令行指定的语言、下拉框却显示简体中文」这种不一致。
- **`--shutdown` 是空操作**：命令行注入的系统集成实现只写一行日志和一句英文提示，不执行任何系统命令；
  真正的关机实现在另一个服务里，五份帮助却都承诺「全部完成后请求关机」。
  命令行是否要真的关机属于会改变机器状态的动作，需用户拍板；在拍板前至少要让行为诚实
  （显式拒绝或改帮助），不要留「说了会做、静默没做」。
