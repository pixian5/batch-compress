# 外部程序与许可经验

> 项目自己不实现压缩算法，全部交给外部命令行程序；「程序能跑起来」的第一怀疑对象是二进制定位。

## 1. 可执行文件查找要有明确的候选路径表，并逐个校验

`7zz` 的顺序是：显式配置路径 → 程序目录 `tools/7zip/<平台>/7zz` → 当前工作目录同类路径 → 系统路径
（macOS 含 `/opt/homebrew/bin/7zz`；Linux 含 `/usr/bin/7zz`；Windows 查 `Program Files/7-Zip/7z.exe`）。
每个候选都要验证存在、可执行、架构正确，失败原因写进诊断输出。
**当前核实**：`SevenZipArchiveEngine.GetCandidatePaths()` 与 `TryValidateExecutable()`。

## 2. 从访达（Finder）启动时 `PATH` 不可靠

打包脚本因此把 `7zz` 及许可证、说明、历史文件放进 `.app/Contents/MacOS/tools/7zip/macos/` 固定相对路径，
而不是指望系统 PATH。命令行里能跑通、双击应用跑不通，优先查这条。

## 3. 按目标平台（RID）复制工具，别把三份都塞进产物

csproj 用 `RuntimeIdentifier` 条件决定复制 `macos/` / `linux-x64/` / `linux-arm64/` 哪一份；
macOS 那份是通用二进制（universal，含 x86_64 + arm64）。
打包脚本会拒绝非 `Mach-O universal` 的 `7zz` 和非 arm64 的 RAR，避免装好之后才发现执行失败。

## 4. RAR 许可：不要分发「分发包的独立部分」

win.rar GmbH 协议第 3a 条禁止未经书面许可分发官方包的独立组件（UnRAR 除外），
第 3b 条禁止把未授权试用版打包进其它软件包。
**已落实的决策 B**：`tools/rarLinux/` 保存官方 `rarlinux-x64-723.tar.gz` 的**完整未修改**解包内容
（`rar`、`unrar`、`default.sfx`、`license.txt`、`order.htm`、`rar.txt`、`rarfiles.lst`、
`readme.txt`、`whatsnew.txt`、`acknow.txt`、`makefile`），Linux x64 构建整体复制，不再只挑一个 `rar`。
macOS 私有打包仍要求用户提供 `BATCHCOMPRESS_RAR_DIR` 自行注入，授权责任由用户承担。
**当前实测核实**：目录下实际为 **11 个文件**。许可风险说明文档列出同样 11 个名字却写「共 12 个文件」，
是历史文档的计数笔误，不要照抄；见 [覆盖清单](13-文档覆盖清单.md)。
csproj 的 `linux-x64` 条件块确实整体复制该目录。

## 5. 只有 `rar` 能创建 RAR，`unrar` 不行

引擎路由里「创建 rar」与「解压 rar」是两条不同路径；解压时先由 `ArchiveVolumeResolver`
判断归档种类再分派，格式字段缺失时才有回退逻辑。

## 6. 退出码 `0` 和 `1` 都可能代表成功或非致命警告

WinRAR / 7-Zip 的 `1` 常表示「有警告但完成了」，不要一律当失败；
真正需要区分的是引擎返回结构里的 `Success` 与错误消息，而不是裸退出码。
另外 `7zz` 没有「创建后自动测试」开关，成功创建后要显式再跑一次 `t` 命令，
且分卷归档必须以**实际首卷**为测试入口（基础输出文件可能不存在）。

## 7. 升级官方 `7zz` 时的最小动作

从官方发布页下载三个平台的压缩包 → 校验 SHA-256/SHA-512 → 只替换 `7zz` 与随包
`History.txt` / `License.txt` / `readme.txt`，保留仓库既有目录约定（不引入 `7zzs`、`MANUAL/`）→
确认可执行位 → 同步 README 与许可文档里的版本号和校验和。
当前仓库为 7-Zip **26.05**（macOS 通用二进制、Linux x64、Linux ARM64 三份统一）。

## 打包成功 ≠ 功能可用：Windows 产物没有随包归档器（2026-11-16 整体分析）

- 发布配置里只有 macOS、Linux x64、Linux ARM64 三组复制条件，仓库 `tools/7zip/` 也只有这三份官方程序；
  **Windows 的发布配置没有任何对应条目**，Windows 打包脚本打出的 zip 里只有主程序和许可文件。
- 代码里 Windows 分支的第一个候选路径指向一个并不存在的随包目录，第二个才找系统默认路径安装的 7-Zip。
  用户没装、或装在非默认位置时，7z、zip、tar、gz、bz2、xz、wim 的压缩解压都不可用，
  而报错只说「找不到命令行程序」，不会告诉用户该装什么、装到哪。
- 本机的 87 项单元测试、33 项经验实测、149 项夹具、4 条界面冒烟**全在 macOS 跑**，
  一条都碰不到 Windows 这段逻辑。所以「打包成功」一直被当成「功能可用」。
- 本机至少可以补一条「产物结构契约」检查，把「Windows 包里应该有什么」写成可复跑的断言；
  但这类检查只验证产物结构，**不能替代在 Windows 机器上实际启动**。
- 是否随包带 Windows 版 7-Zip 属于需要用户拍板的事项（涉及其再分发条款与来源确认），
  不要擅自往仓库里加第三方可执行文件。

## Windows 缺少 7-Zip 时自动下载安装（2026-11-16，0.8.12 用户决定）

用户明确决定：**Windows 产物不随包带 7-Zip，没有就自动从官网下载安装**。实现是
`Core/Services/SevenZipProvisioner.cs`，几条约束值得记住：

- **只装当前用户目录**：`%LOCALAPPDATA%\BatchCompress\7zip`，不需要管理员权限，
  不写系统目录、不改环境变量；卸载时删掉这个文件夹即可。
- **优先拿官方校验值**：7-Zip 官网现在把最新版下载指向 GitHub Releases，
  页面本身不再提供 `.sha256` 链接；但 GitHub 发布接口的资产对象带 `digest`（`sha256:...`），
  用它校验比「只靠 HTTPS」可靠。接口不可用才退回下载页解析，并在日志里注明没有校验值。
- **先 MSI 管理式解包，失败再 EXE 静默安装**：`msiexec /a ... /qn TARGETDIR=...`
  只展开文件、不注册组件；EXE 用 `/S /D=<目录>`。两条路都可能被企业策略拦截，
  失败时要给出可操作的手动下载地址，不能只说「找不到程序」。
- **安装后必须验证**：跑一次 `7z.exe i` 确认输出含 `7-Zip`，并确认 `7z.dll` 与 `7z.exe` 同目录；
  只有 exe 没有 dll 时 WIM 等格式不可用，应判定安装失败并重试。
- **触发时机**：界面在窗口显示后后台检查、执行前再确保一次；命令行在参数校验与试运行判断之后检查。
  `--dry-run` 不应产生下载副作用；下载进度写标准错误，不能污染结构化输出的标准输出。
- **本机（macOS）只能测纯逻辑**：发布接口 JSON 解析、下载页解析、目录归位、SHA-256 计算；
  真正的 MSI/EXE 安装必须在 Windows 上确认，别把单元测试通过当成安装流程已验证。

## 不要把「当前工作目录」当作外部程序的查找路径（2026-11-16 整体分析）

`SevenZipArchiveEngine` 的 macOS/Linux 候选里有一条
`Directory.GetCurrentDirectory()/tools/7zip/.../7zz`，而校验逻辑会给候选补执行位并运行它。
用户在下载来的项目目录、临时目录或任何可写目录里运行命令行时，目录里的伪造 `7zz` 就会被执行。

- **0.8.16 已移除当前目录候选**：生产路径只信任 `AppContext.BaseDirectory` 与系统安装位置；
- 需要自定义时用显式 `BATCHCOMPRESS_7ZZ_PATH`，它优先于默认候选；
- 回归测试用源码守护锁住：`SevenZipArchiveEngine.cs` 不得再出现 `Directory.GetCurrentDirectory()`。
- 同理，`which rar` 依赖 PATH 是用户自己的选择，可以保留；但“当前目录”不是 PATH，不能默认信任。
