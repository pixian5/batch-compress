# 进程边界与并发经验

> 所有外部归档程序只经过 `ArchiveProcessRunner` 这一道门；并发问题几乎都出在「共享状态」上。

## 1. 参数逐项放进 `ArgumentList`，绝不拼 Shell 字符串

`ProcessStartInfo.ArgumentList.Add(...)` 逐项传参，天然处理路径里的空格与引号，也避免注入。
用于日志的「完整命令行」只是展示用，是另外拼出来的字符串，不参与实际启动。
`UseShellExecute=false`、`CreateNoWindow=true`、重定向 stdout/stderr。

## 2. stdout 与 stderr 必须并行异步读取

两个 `ReadToEndAsync()` 同时挂上再等进程退出；若先等退出再读，管道缓冲区写满会死锁。
日志保留原始输出（含明文密码），这是明确的诊断取舍，不要自作主张加脱敏。

## 3. 取消要杀整棵进程树

`Kill(entireProcessTree: true)` 后还要等待退出，并把两个读取任务收干净再抛出取消异常。
只杀父进程会留下正在写归档的子进程，产生半途废档。

## 4. 并发里的共享状态用一把锁，上报用克隆快照

`progressInfo` 的读写、成功/失败计数、累计大小、进度上报全部在同一把锁内，
上报前克隆一份快照，避免消费者读到「计一半」的撕裂状态。
默认并发度为 1，串行路径原样保留，保证升级后旧行为零漂移。

## 5. 「大小上限」和「取消」要用两个不同的令牌

| 场景 | 令牌 | 行为 |
| --- | --- | --- |
| 达到总大小上限 | 闸门令牌 | 只让**还没启动**的任务放弃排队，在途引擎自然完成，不产生废档 |
| 用户按 Ctrl+C | 引擎令牌 | 立即传播到全部在途引擎，终止整个进程树 |

把两者混在一个令牌上，要么达限时杀出半截归档，要么取消后排队任务还在启动。

## 6. 关机只在「非取消的正常结束」路径触发恰好一次

判断点唯一放在全部任务完成之后；取消异常向上传播时不会到达这里。
测试要显式断言 `ShutdownCalls` 的精确次数，而不是「有没有调用」。

## 7. 并发下完成顺序不等于输入顺序

结构化输出（NDJSON，逐行 JSON 事件流）的消费方必须按 `source` 字段关联条目，
不能靠行号或顺序推断是哪一项。帮助与命令行参考里专门写了这一章。

## 8. 自动化脚本测「取消」要绕开信号被忽略的坑

**2026-11-05 实测新知**：非交互 shell 启动的后台作业默认**忽略 SIGINT（中断信号）**。
直接 `kill -INT <后台PID>` 会被丢弃，压缩照常跑完返回 `0`，看起来像「取消功能坏了」，
实际是测试方式错了。前两次尝试都因此失败。

**做法**：在子进程里先重置信号处置再启动程序，例如
`zsh -c 'trap - INT; exec "$@"' _ dotnet ... &`，随后 `kill -INT` 才会被程序的
`Console.CancelKeyPress` 捕获。同时要让任务足够长（多份较大文件串行压缩），
否则信号到达时任务已经结束。

实测确认：退出码 `130`，日志记录 `Operation cancelled by user (Ctrl+C)` 与
`Operation was cancelled`，且 `pgrep -x 7zz` 查不到残留进程——
印证了「取消杀整棵进程树」这条约束确实生效。

## 9. 并发度不要让用户凭感觉填，给一个硬件感知的推荐值

**2026-11-15 批次 18（P4-2）实测**：低内存设备上同时跑多个 7zz 高压缩任务容易 OOM
（内存耗尽）或被系统强杀。`ConcurrencyAdvisor` 的做法是：

- 处理器上限 = 核数 / 2（留一半给界面与磁盘 IO）；
- 内存上限 = 可用内存 / 512 MiB（单个归档进程的保守预算）；
- 取较小值并钳制在既有 1–16 区间；内存读不到就保守返回 1；
- 用 `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes` 读内存，跨平台且尊重容器限制，
  不调用 `sysctl` / `/proc/meminfo` 这类平台专属命令。

**容易踩的两点**：① 默认并发度必须保持 1 串行，只有用户主动选 `auto` 或点「应用推荐」才改，
否则老脚本行为会漂移；② 结构化输出（NDJSON，逐行 JSON）模式下，自动推荐的
人类可读提示必须写 **stderr**，写 stdout 会让消费方解析失败。
另外「试运行会提前返回」这个老坑在这里又出现一次：`--dry-run` 不走构建批次选项，
所以推荐值的解析要提前到试运行判断之前并缓存，预检才能看到。

## 10. 想「提前终止」坏块，先确认错误从哪条流出来

**2026-11-15 批次 19（P4-1）实测**：构造损坏的 1 MiB 分卷后，
官方 `7zz` 把 `ERROR: CRC Failed : big.bin` 写在**标准错误（stderr）**，
标准输出只有 `Sub items Errors: 1` 这类汇总。
而改造前进程边界只对标准输出做逐行回调、标准错误是等进程结束整段读取，
所以「从进度流捕获坏块」根本做不到——必须把标准错误也改成逐行流式读取。

几条配套约束：

- 只认明确的数据损坏（CRC 失败、数据错误、归档意外结束、无法作为归档打开、分卷缺失）；
  **不要认密码错误与普通警告**，7-Zip 在某个条目密码错误时仍可能继续处理其它条目，误杀会中断整批。
- 用**独立的联动取消令牌**终止当前进程，并且与外部用户取消严格区分：
  致命错误转成失败结果走既有回滚，用户取消仍按取消语义抛出，绝不能混。
- 解析回调自身抛异常要降级为「不提前终止」，解析问题不能影响归档结果。
- 未传致命解析器的路径（压缩等）保持原行为逐字节不变，避免顺手改坏老功能。

## 关机要按平台选命令，macOS 不能直接用 shutdown（2026-11-16，0.8.12）

用户要求命令行 `--shutdown` 真正关机，于是把关机/取消关机抽成
`Core/Services/SystemPowerService.cs`，命令行与界面共用。踩点如下：

- **macOS 的 `/sbin/shutdown` 需要 root**，普通用户执行会直接失败；原来的界面实现就是这条，
  失败时只弹「可能需要管理员权限」。改用 `osascript` 请求 System Events 关机，以当前用户身份执行。
- 用 AppleScript 时把 `delay 60` 放进脚本自身（`osascript -e "delay 60" -e "tell application ..."`），
  既保留一分钟取消窗口，又不用我们自己起定时器；取消就是结束这个待执行的 osascript 进程。
- 应用包必须在 `Info.plist` 写 `NSAppleEventsUsageDescription`，否则系统无法就自动化控制
  弹出授权提示，脚本会被拒绝。这是很容易漏的一步。
- Windows 用 `shutdown /s /t 60`、取消 `/a`；Linux 用 `shutdown -h +1`、取消 `-c`。
  所有参数走 `ArgumentList`，不拼 Shell 字符串。
- **绝不能在开发机上实测真实关机**。验证方式只能是单元测试检查三种平台的命令与参数，
  加上「命令行实现确实调用了关机服务」的源码/接线断言；真实行为留给用户在可接受关机的环境确认。
- 命令行失败不能静默：提交关机请求失败时写标准错误，不能只在日志里写一句「已请求」。
