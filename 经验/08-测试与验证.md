# 测试与验证经验

## 1. 测试是控制台程序，不是 `dotnet test` 体系

`BatchCompress.Avalonia.Tests` 是输出 59 项检查的可执行程序，
`BatchCompress.Avalonia.sln` **只包含主项目**，必须单独指定 csproj 运行：

```bash
dotnet run --project BatchCompress.Avalonia.Tests/BatchCompress.Avalonia.Tests.csproj --nologo
```

用 `dotnet test` 或只构建解决方案，会误以为「测试跑过了」，其实一项都没执行。

## 2. 测试工程链接生产源码

csproj 关闭默认编译项，用 `<Compile Include="..\Core\**" Link="...">` 编译交付代码本身。
新增服务类后**必须**在该 csproj 登记，否则测试根本没覆盖到它——这是很容易漏的一步。

## 3. 加新功能先补断言，再动实现

「表征测试」锁的是可观察行为：消息文本、七类计数、关机时机、文件系统副作用、
取消时的临时目录残留。用脚本化假引擎（`ScriptedArchiveEngine`）控制延迟与取消时机，
覆盖「进循环前取消」「引擎执行中取消」两条路径。

## 4. 并发测试至少连跑三遍

并发缺陷常常是概率性的。批次 5 的做法是新增并发用例后重复运行三次都稳定才算通过。

## 5. 端到端夹具与单元测试是两层

`测试夹具/全功能测试/run-all-tests.sh` 覆盖真实文件系统与命令行场景（现约 149 项）；
控制台测试覆盖逻辑与边界。两者都要跑，只跑一层会漏掉真实归档行为。
官方 `7zz` 真实带密码压缩/解压、归档测试、解压后逐字节核对内容，属于关键回归项。

## 6. 改完先在小规模测试环境验证，再考虑真实目标

新代码先用测试目录、测试卷、测试数据跑通；用户没明确点名真实目标时默认用测试环境。
`--dry-run` 是安全的预检手段，只列任务、不创建输出目录、不写归档。

## 7. 收尾要验证，不要「我记得跑过了」

一轮改动的检查清单：构建 0 警告 0 错误 → 全量测试通过 → Release 构建 →
`scripts/smoke-test.sh` 秒级冒烟（多语言帮助、参数异常阻断、三平台打包自检）→
检查有无残留进程/临时目录 → 提交推送。
留下可核对的输出，不要只在脑子里确认。

## 8. 端到端夹具脚本必须用 zsh 运行

**2026-11-15 实测踩坑**：`测试夹具/全功能测试/run-all-tests.sh` 的 shebang（脚本解释器声明）
是 `#!/bin/zsh`，内部用了 zsh 专有语法 `${0:A:h:h:h}` 与 `print`。
用 `bash 测试夹具/全功能测试/run-all-tests.sh` 调用会报
`print: command not found`，且 `BASH_SOURCE` 为空导致输出路径被解析到根目录，
出现 `/测试夹具/.../生成物/xxx: No such file or directory`。

正确调用：

```bash
zsh 测试夹具/全功能测试/run-all-tests.sh
# 实测 TOTAL PASS=149 FAIL=0
```

**教训**：CI（持续集成）里调用这类脚本要显式写解释器，不能只写脚本路径；
本仓库 `ci.yml` / `release.yml` 目前仍未调用它，建议补上（见当前待办）。
另外该脚本的 149 项夹具依赖真实 `7zz` 与本机路径，先只在 macOS runner 落地更稳。

## 9. 测试工程新增文件要显式登记

测试 csproj 关闭了 `EnableDefaultCompileItems`，新增 `.cs` 文件必须手写
`<Compile Include="...">`。批次 18 新增 `Program.ConcurrencyTests.cs` 时漏登记，
直接报 `CS0103: The name 'TestXxx' does not exist in the current context`。
同理，新增生产服务类也要在测试 csproj 里 `<Compile Include="..\Core\Services\...">` 链接，
否则测试根本没编译到那份代码。

## 界面冒烟只做三件能稳定复跑的事

**2026-11-16 批次 25 实测**：`测试夹具/界面冒烟/run.sh` 用三条用例覆盖交付物：

1. 启动后主程序与状态栏帮助进程都存在（两个 `pgrep -x`）；
2. 应用内 `--version` 与仓库 `VERSION` 一致；
3. 用交付产物跑一次真实最小压缩，退出码 0 且产出至少一个 `.7z`。

**不要**把「按坐标点按钮」做成硬门禁：需要 macOS 辅助功能授权，受窗口位置与缩放影响，
换台机器就红。脚本只关闭自己启动的实例，用户原本开着的应用不动。

## 界面冒烟必须核对「运行中窗口」的版本（2026-11-16，0.8.9）

- 实测踩过：可执行文件已是 `0.8.9`，但 `open` 复用了上一批留下的旧进程，窗口标题仍是
  `v0.8.8`；只比 `--version` 与 `VERSION` 会假阳性。新增读取运行中窗口标题并断言包含当前版本。
- 读不到标题（辅助功能未授权）时打印 SKIP，不误报 PASS，也不影响其余用例。
- 分批验证脚本要覆盖「提前返回路径」：试运行、参数校验失败、取消、异常都要断言附加产物是否产出。
- 修复类批次的回归测试要成对补齐：代码路径（强制写入、抑制补记、临时文件权限）与
  输出契约（英文文案、CSV 防护、中性标记翻译、空行保留）都要有断言。

## 绿灯不等于测到了：149 项夹具的有效性复核（2026-11-16 整体分析）

- **别断言字段名**：`check_contains ... "Skipped"` 检查的是汇总行里的字段名，而汇总行无论
  有没有真的跳过都固定打印 `Skipped=`，`Skipped=0` 也会通过。要断言精确值（如 `Skipped=1`），
  并顺手验证归档是否真的生成、内容是否一致。
- **文件缺失必须判失败**：`check_not_contains` 在目标文件不存在时直接判通过；
  `check_sha` 在两个文件都不存在时两边哈希都是空串，也会判通过。前置步骤失败因此会被掩盖。
  脚本没有 `set -e` / `pipefail` 兜底时更危险。
- **只比退出码的用例要补产物校验**：约 96/149 项只比进程退出码，空归档、解压到错目录、
  跳过策略失效但返回 0 都能绿灯通过。
- **开测前要有「产物新鲜度」守卫**：夹具固定跑 Release 且用 `--no-build`，经验脚本只构建 Debug，
  两者之间没有检查被测程序集是否比最新源码新。当前恰好是新的，但下次改完源码只跑经验脚本就会测到旧产物。
  这与既有的「开测前确认载荷最新」规则是同一件事，应写进脚本而不是靠人记。
- **静态夹具要真的被引用**：`密码本.txt`、`压缩路径清单.txt`、`重复路径清单.txt` 等 7 个文件
  在全部脚本里引用次数为 0，里面混合格式、大小写扩展名、重复项、缺失项、元数据文件等真实输入全没跑；
  脚本实际只用运行时生成的两行密码本。接线前先核对其中引用的目录名是否已与脚本产出失配。
- **界面层零自动化覆盖的后果**：测试工程为保持轻量不引用界面框架，所谓「界面测试」多为读源码
  做字符串匹配，运行时绑定、命令能否执行、属性通知是否发出都验证不到。
  页签显隐、串行进度串台这类缺陷因此长期没被发现；抽可测的纯逻辑进测试工程比硬加界面依赖更划算。
- **产物结构自检不能替代实机运行**：读取压缩包清单只能证明「包里该有的文件在」，
  不能证明 Windows / Linux 程序能启动、随包二进制权限正确。这两类检查要分开表述，别互相冒充。
- 夹具说明文档也有口径漂移：README 写 Debug / 120 项 / 八种格式分卷覆盖，脚本实际是
  Release / 149 项 / 分卷只覆盖 7z、zip、rar、tar。按旧说明操作会用旧产物跑出一份无效结论。

## 当前验证基线（2026-11-17，0.8.17）

- **106 项**单元测试、**43 项**经验实测、**155 项**端到端夹具、4 条界面冒烟、交付冒烟。
- SDK / 目标框架：`.NET SDK 11.0.100` / `net11.0`。
- 新增测试：操作完成信号、覆盖失败恢复旧归档、目录大小排除符号链接、共享密码脱敏、报告/NDJSON 脱敏、7-Zip 不信任当前目录、CLI TXT 诊断条目、覆盖备份启动恢复。
- 界面默认值这类「启动时就确定」的状态，优先让程序把实际值写进运行日志（本项目为
  `GUI_DEFAULTS`）再读日志核对；**不要用整屏截图**，既会截到用户其它窗口，也不如日志精确。
- 新增的 7-Zip 自动安装与关机命令属于「纯逻辑可测、真实行为不可在本机执行」的两类：
  前者需要 Windows 实机，后者会关掉开发机。测试只能覆盖地址解析、校验和、目录归位、
  命令参数构造与接线；文档里必须明确写「待实机」，不能写成已验证。

### 诊断版本与 TXT 缺失项的测试（0.8.17）

- 诊断包版本不要靠“程序目录里有没有 VERSION 文件”来测；测试目录本来就没有它，
  必须断言摘要版本等于 `ApplicationInfoService.ReadApplicationVersion()`，并用打包应用实跑一次。
- TXT 缺失项要同时测两层：纯合并函数把缺失/缺卷/歧义条目补进任务列表；
  真实 CLI 用“有效归档 + 不存在归档”跑一次，断言 `Success=1, NotFound=1` 且有效文件解压成功。
- 完全不存在且没有同组残卷的路径应在 `Resolve` 前按 `NotFound` 计，
  否则会被“单名推断分卷组”误判成 `IncompleteVolumes`。

### 覆盖替换与目录大小的测试（0.8.15）

- 覆盖模式不能只测“成功后旧文件没了”，必须测“失败后旧文件还在且内容不变”：
  旧卷先改名备份，失败时先清理新卷再恢复备份；恢复后要把旧路径重新纳入
  `PreExistingOutputFiles`，否则管线随后的失败清理会把刚恢复的旧文件当残片删掉。
- 目录大小测试要造一个指向自身的符号链接；`Directory.EnumerateFiles` 使用
  `AttributesToSkip = ReparsePoint` 后才能在 1 秒内结束且不越界统计。
- 关窗流程的完成信号要单独抽类测试，不要只断言 `IsOperating` 布尔值；
  等待的是 `finally` 真正执行完，而不是属性变 false 的瞬间。

### .NET 11 升级的两个坑（0.8.14）

- **脚本里的 TFM 路径会过期**：`verify.sh` 写死了 `bin/Debug/net10.0`，升到 net11 后会读到旧产物，
  出现“版本还是 0.8.13”的假失败。升级目标框架时同步搜索所有 `net10.0` / `net11.0` 路径。
- **NU1510 不是错误但会破坏 0 警告基线**：.NET 11 共享框架自带 `Microsoft.Extensions.Logging.Abstractions`，
  测试工程显式引用会被判定冗余。移除引用，不要用 `NoWarn` 掩盖。
- Avalonia 12.1.6 提供 `net10.0`/`net8.0` 资产，`net11.0` 项目会选用 net10 资产；
  实测全部测试与界面冒烟通过，本次没有升级 Avalonia。

### 0.8.13 夹具加固的教训

- `check_not_contains` / `check_sha` 必须显式要求目标文件存在；否则前置命令失败会被
  「没有出现不该出现的文本」和「两边空哈希相等」掩盖成绿灯。
- 恒真断言往往长得像真断言：`check_contains ... "Skipped"` 匹配的是汇总行固定字段名，
  `Skipped=0` 也通过；要断言精确值 `Skipped=1`。
- 修好辅助函数后要立刻复跑：本次因此抓出一条**引用错文件名**的旧断言
  （`extract-incomplete.stdout` vs `extract-incomplete-volume.stdout`），它靠“文件缺失即通过”空过了很久。
- 关键压缩/解压用例至少补两类断言：产物存在、解压内容与原始文件 SHA-256 一致。
- 进度行本地化后，不要再用「输出里没有‘成功’二字」判断失败；改为断言输出目录不存在。
