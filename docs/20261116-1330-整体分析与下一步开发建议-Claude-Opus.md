# 整体分析与下一步开发建议（0.8.11）

> 用户原问题：**整体分析项目，给出下一步开发详细建议**
> 分析时间：2026-11-16 13:30　版本：`0.8.11`　分支：`main`　上一提交：`e317944`　工作区：干净
> 性质：**只读分析**，不改动任何产品源码，`VERSION` 不变

## 一、结论摘要

项目早已不是「做完路线、没找到事做」的状态。这一轮把当前代码、测试夹具、打包脚本和双入口实现逐层核过一遍，
**确认了 2 个高优先级缺陷、7 个中优先级缺陷、若干卫生项**，其中两个最要紧的是：

1. **诊断包仍会漏出明文口令**：当自定义密码含空格时，命令行写成 `"-pSuper Secret 123"`（引号包住整个参数），
   现有脱敏规则一条都匹配不上。我用项目里真实的 .NET 正则跑过五种写法，这种形式原样保留。
   诊断包本来是要发给别人协助排障的，等于把密码直接交出去。
2. **149 项端到端夹具里有一条恒真断言**：`check_contains ... "Skipped"` 检查的是汇总行里的字段名，
   而汇总行无论有没有真的跳过都固定打印 `Skipped=`。这条用例永远通过，无法区分「跳过 1 个」和「一个都没跳」。
   同一脚本还有两处「文件不存在反而判通过」的写法，会让前置失败被掩盖。

其余值得先做的：命令行与界面的来源校验口径不一致（一条 `--dry-run` 实测可复现）、
命令行运行器自己的输出完全没本地化、纯 `--lang de` 启动界面会被系统语言覆盖、
命令行 `--shutdown` 是空操作、默认串行路径的进度对象被复用导致日志可能串台、
页签切换时两个操作按钮的显隐可能卡住、图形界面与命令行的默认压缩参数不一致。

**建议的推进顺序**：先堵明文口令与夹具假绿灯（改动小、风险低、收益直接），
再统一命令行行为与文案，然后补图形界面层的可测试性，最后是交付结构自检。
有三个架构级议题需要你拍板，我把完整说明放在第六节，没有替你决定。

## 四、问题清单

### 4.1 高优先级（建议先做）

#### 【P0-1】含空格密码仍以明文进入诊断包 —— 【实测】

- **现状**：诊断包会把磁盘日志脱敏后打包，定位是「可对外分享」。脱敏规则覆盖 `-p明文`、`-p"明文"`、
  `--password 明文`、`--password=明文`。但当密码里带空格，归档命令会被整体加引号，变成
  `7zz a "-pSuper Secret 123" out.7z`，引号在 `-p` **前面**，现有规则全部落空。
- **证据**：`Core/Services/SevenZipCommandBuilder.cs:141` 与 `WinRarCommandBuilder.cs:131` 都用
  `-p{password}` 连写；`Core/Services/ArchiveProcessRunner.cs:223-236` 对含空格的参数整体加引号；
  `Core/Services/DiagnosticsExportService.cs:60-82` 的正则要求 `-p` 前是行首或空白、引号在 `-p` 之后。
  用项目真实程序集跑 `RedactSensitiveText` 的五种输入，结果如下：

  | 输入 | 输出 | 是否残留明文 |
  | --- | --- | --- |
  | `7zz a -pSuperSecret123 out.7z` | `7zz a -p*** out.7z` | 否 |
  | `7zz a -p"SuperSecret123" out.7z` | `7zz a -p"***" out.7z` | 否 |
  | `7zz a "-pSuper Secret 123" out.7z` | **原样不变** | **是** |
  | `rar a "-hpHead Secret 456" out.rar` | **原样不变** | **是** |
  | `app compress --password=EqualsSecret -e 7z` | `app compress --password=*** -e 7z` | 否 |

- **触发条件**：随机生成的密码是十六进制串、不含空格，所以只有**用户自定义密码或密码文件读入的含空格口令**会触发。
  范围不广，但一旦发生就是明文外泄，而且恰好发生在「准备把日志发给别人」的时刻。
- **不改会怎样**：把诊断包发给同事或厂商排障时，等于连同归档口令一起交出。上一轮刚补了等号形式，
  换一个引号位置就能绕过去，说明这类规则靠逐条穷举容易再漏。
- **建议方向**：短期把规则改成能识别「引号包住整个参数」的形态并补边界用例；
  中期更稳妥的是在生成日志时就把「可复制执行的命令」与「日志展示文本」分开，日志侧统一写占位符。
  但后者与「命令日志按既定策略保留明文密码」冲突，需要你确认边界——我没有擅自改这条策略。

#### 【P0-2】Windows 产物没有随包归档器，功能依赖用户预装 —— 【确认】

- **现状**：macOS 与 Linux 的发布配置会把仓库自带的 7-Zip 官方命令行程序复制进产物；
  Windows 的发布配置**没有任何对应条目**，仓库里也没有 Windows 版二进制目录。
  代码里 Windows 分支的第一个候选路径指向一个并不存在的随包目录，第二个才找系统安装的 7-Zip。
- **证据**：`BatchCompress.Avalonia.csproj:43-56` 只有 `osx-*`、`linux-x64`、`linux-arm64` 三组条件；
  `tools/7zip/` 下只有 `macos`、`linux-x64`、`linux-arm64`；
  `Core/Services/SevenZipArchiveEngine.cs:171-179` 的 Windows 候选先找随包 `7z.exe`、再找
  `%ProgramFiles%\7-Zip\7z.exe`；`scripts/package-windows.sh:44-49` 打出的 zip 里只有主程序和许可文件。
- **不改会怎样**：Windows 用户若没把 7-Zip 装到默认路径，7z、zip、tar、gz、bz2、xz、wim 的压缩解压都不可用；
  本机的 149 项夹具、87 项测试、4 条界面冒烟**一条都覆盖不到这个分支**，因为它们全在 macOS 跑。
  「打包成功」被当成了「功能可用」。
- **建议方向**：见第六节需要拍板的第一件事。本机至少可以补一条「产物结构契约」检查，
  把「Windows 包里应该有什么」写成可复跑的断言，避免继续靠假设。

### 4.2 中优先级

#### 【P1-1】149 项夹具存在恒真断言与假通过 —— 【确认】

- `测试夹具/全功能测试/run-all-tests.sh:189` 用 `check_contains ... "Skipped"` 验证「跳过已处理」策略；
  而 `HeadlessBatchRunner.cs:231-236` 无条件打印 `Skipped={数量}`。`Skipped=0` 也匹配成功，这条永远通过。
- 同脚本 `:92-99` 的 `check_not_contains` 在文件不存在时直接判通过；`:101-107` 的 `check_sha`
  在两个文件都不存在时，两边哈希都是空串、`"" == ""` 也判通过。脚本没有 `set -e`/`pipefail` 兜底。
- 约 96/149 项只比对退出码，不检查归档是否真的生成、内容是否一致；`compress-rar`、`compress-zip`
  等没有产物校验。
- **不改会怎样**：空归档、解压到错目录、跳过策略失效但进程返回 0，全部可能绿灯通过。
  这是「验证链有效性」问题，比少测几个格式严重。
- **建议方向**：把 `Skipped` 改成精确值 `Skipped=1` 并补产物校验；两个辅助函数改成「文件缺失即失败」；
  给关键压缩/解压用例补内容比对。

#### 【P1-2】命令行前置存在性校验与界面口径不一致 —— 【实测】

- `HeadlessBatchRunner.cs:366-385` 在执行前用**原始路径**逐个检查，只要有一个不存在就整批退出码 2；
  而界面侧与服务层的来源收集器明确「不做存在性过滤，缺失项统一按『未找到』计数，其余照常处理」。
- 实测（只跑不写归档的试运行）：
  - 输入一个存在目录 + 一个不存在目录 → 输出 `Error: 来源不存在: .../missing`，存在的那项也不处理；
  - 输入一个真实文件但路径末尾带斜杠 → 同样被拒；而源码里专门有个路径规范化函数就是为修这个缺陷写的，
    它在校验**之后**才执行，注释却声称已经生效。
- **不改会怎样**：同一份来源清单在界面能跑完（记一条未找到），在命令行直接全批失败；
  尾斜杠这个已修过的缺陷在命令行又回来了。
- **建议方向**：校验前先做路径规范化；把「有一个缺失就整批失败」改成与界面一致的逐项计数。
  代价是命令行的「快速失败」契约会变化，试运行输出和五语言帮助说明要同步改。

#### 【P1-3】命令行运行器自己的输出完全没本地化 —— 【实测】

- 历史上「命令行不构造界面、语言恒为简体中文」的根因**已经修好**（`Program.cs:88` 会同步 `--lang`，
  服务层消息也走本地化资源）。但 `HeadlessBatchRunner.cs` 里几十处终端文案仍是硬编码英文，
  另有两处硬编码中文：`读取密码失败: {0}`（:361）、`来源不存在: {0}`（:379）。
- 实测：`--lang en` 下运行不存在的输入，错误仍是 `Error: 来源不存在: ...`；
  默认语言跑真实批次，则是英文 `Completed: ...` 配中文服务消息。
- **不改会怎样**：`--lang` 只切了一半，脚本解析与人工排障时语言不稳定；历史文档里这条结论已过时，
  照旧结论去修会做重复工作。

#### 【P1-4】纯 `--lang de` 启动界面会被系统语言覆盖 —— 【确认】

- 五份命令行帮助都写了「单独使用 `--lang` 时直接以该语言启动图形界面」，`Program.cs:82-88`
  也确实先设好了语言；但界面状态类字段初值固定 `zh-CN`（`MainWindowViewModel.cs:100`），
  构造函数又无条件调用系统语言检测（:523），把命令行指定的语言覆盖掉。
- 更细的一层：当系统语言恰好是简体中文时，给 `SelectedLanguage` 赋同值不会触发属性变化通知，
  于是**实际界面是命令行指定的语言、下拉框却显示简体中文**。
- **不改会怎样**：文档承诺的行为不兑现，且出现语言与选择器不一致的怪现象。

#### 【P1-5】命令行 `--shutdown` 是空操作 —— 【确认】

- `HeadlessBatchRunner.cs:641-652` 注入的系统集成实现只写一行日志和一句
  `System shutdown requested.`，不执行任何系统命令；而真正的关机实现在
  `Core/Services/SystemIntegrationService.cs:92-101`。五语言帮助都承诺「全部完成后请求关机」。
- **不改会怎样**：命令行批处理结束后静默不关机、不报错，用户以为会关机。
  这项是否要修需要你拍板（见第六节第二件事），因为自动关机属于有副作用的操作。

#### 【P1-6】默认串行路径复用同一个可变进度对象 —— 【确认】

- `Core/Services/Pipeline/BatchExecutionPipeline.cs:103,158` 在串行分支直接把共享的进度对象传给回调；
  并发分支全部用克隆对象（:266 等），代码注释自己写明原因是「回调可能异步投递，必须防止串台」。
  而界面默认并发度就是 1（`MainWindowViewModel.cs:309`），也就是说**默认走的是没保护的那条路**。
- 界面的进度回调经 `Progress<T>` 异步投递到界面线程，所以成功/失败记录里的文件名、计数
  有可能已被下一项改写。测试工程里另建了「克隆进度」辅助类、注释也点明了这个现象，但表征测试只断言最后一条，
  恰好避开。
- **不改会怎样**：批处理日志里的逐项记录可能对不上实际文件，排查时误导。
- **建议方向**：串行分支也用克隆对象，并补一条「第 1 项消息不被第 2 项覆盖」的断言。改动很小。

#### 【P1-7】页签切换时两个操作按钮的显隐可能卡住 —— 【确认】

- `MainWindowViewModel.cs:136-145` 的页签属性通知列表列了 7 个相关属性，
  **唯独漏了** `IsCompressionActionVisible` / `IsDecompressionActionVisible`（:154-155），
  而主界面的「压缩」「解压」两个按钮正是绑这两个属性（`Views/MainWindow.axaml:266,270`）。
- 页签变化时，若「上一次操作页」没变，代码不会补发通知，按钮显隐会停在上一页状态。
- **不改会怎样**：用户切到「开始」页可能看不到该出现的按钮，或切到日志页按钮还亮着。
  这类问题**无法被现有 87 项测试发现**——测试工程根本没编译界面状态类（见 P2-1）。

#### 【P1-8】界面与命令行的默认参数不一致 —— 【确认】

| 参数 | 命令行 | 图形界面 |
| --- | --- | --- |
| 压缩级别 | 3（标准） | 1（最快） |
| 恢复记录 | 3% | 0（关闭） |
| 分卷 | 默认不分卷 | 默认开启、20 GB 一卷 |
| 分卷单位 | 支持 b/k/m/g/t | 只有 g/m/k |

同一份任务在两个入口的默认产出不一样，且没有一张对照表说明差异。是否统一需要你拍板（见第六节第三件事）。

#### 【P1-9】Windows 上命令行输出可能不可见 —— 【确认配置 / 待实机】

- `BatchCompress.Avalonia.csproj:4` 是 `WinExe`（Windows 图形子系统）。
  同一个可执行文件既做界面又做命令行，`--help`、`--version`、进度、错误信息全走标准输出/错误。
- Windows 图形子系统进程默认不附着父控制台，从命令提示符直接运行时文本可能被丢弃
  （重定向到文件或管道时又可见）。**配置事实确定，具体表现必须在 Windows 机器上确认**，本机无法验证。
- **不改会怎样**：若确实如此，Windows 用户几乎无法使用命令行入口，与「双入口」定位冲突。
  修法（拆一个控制台入口，或启动时附着父控制台）属于架构改动，需拍板。

### 4.3 卫生项与验证链盲区（按价值排序）

1. **夹具说明文档已过期**：`测试夹具/全功能测试/README.md` 写「完成 Debug 构建后运行」「实测 120 项」
   「八种格式单卷/分卷均有检查」；而脚本固定跑 **Release --no-build**、实际 **149 项**、
   分卷只覆盖 7z/zip/rar/tar。按 README 操作会用旧的 Release 产物跑出一份无效结论。
2. **7 个静态夹具文件零引用**：`密码本.txt`、`压缩路径清单.txt`、`重复路径清单.txt`、
   `附件清单.txt` 等在全部脚本里引用次数为 0。它们包含混合格式、大小写扩展名、分卷、重复项、
   缺失项、`.DS_Store` 等真实输入，全都没跑；脚本实际只用运行时生成的两行密码本。
   结果：「密码本模式」的端到端覆盖其实只有 2 行 7z。
3. **产物新鲜度没有守卫**：夹具跑 `--no-build` 的 Release，经验脚本只构建 Debug，
   两者之间没有任何「产物是否比源码新」的检查。当前恰好是新的，但下次改完源码只跑经验脚本就会测到旧产物。
   这条与你既有的「开测前确认载荷最新」规则直接相关。
4. **图形界面层零自动化覆盖**：测试工程为保持轻量不引用 Avalonia，界面状态类、代码隐藏、
   会话类、系统集成类都没进编译范围。所谓「界面测试」实为读源码文本做字符串匹配，
   不验证运行时绑定或命令能否执行。P1-6、P1-7、事件订阅未退订这类缺陷因此长期没被发现。
5. **事件订阅与资源释放**：界面状态类订阅了静态语言服务的事件且捕获自身引用，全仓库没有退订；
   图形界面创建的文件日志器（`IDisposable`）直到进程退出才释放；数据上下文切换时不对旧实例解绑。
   单窗口场景影响有限，但会阻碍把界面层纳入测试。
6. **失败清理被调用两次**：适配器内部与执行管线各调一次失败回滚，当前因有快照幂等而通常不出错，
   但每次失败多一次全目录扫描；并发共享输出目录时存在把别的项目新写文件误判为残留的窗口。
7. **退出码 1 被当成功**：7-Zip/RAR 的「警告」退出码 1 被判定成功，随后若开启「处理后删除/移动源文件」
   仍会执行。7-Zip 的 1 也可能表示部分文件未处理，是否会造成源文件丢失需要构造不可读文件实测。
8. **格式覆盖**：52 个「仅解压」格式与 65 个扩展名别名（`.apk`、`.docx`、`.msi` 等）在格式目录里声明了，
   但从未用随包 7-Zip 真解过一次。
9. **帮助文本双轨**：五份命令行帮助是独立的大段常量，与选项定义、JSON 词条三处手工维护，
   没有测试守护对应关系，已可见轻微的占位符漂移。
10. **引擎错误文案中英混杂**：RAR 引擎全英文、7-Zip 引擎全中文，都不走本地化资源，
    最终混进界面失败日志。
11. **本地化缺键回退是静默的**：加载器对缺键只写 `Debug.WriteLine`，发布构建里这句会被移除；
    当前五份资源 324 键齐全，但未来漏翻译时非中文界面会静默显示中文。现有的一致性测试守住了键集合，
    没守「值是否真的翻译」。
12. **接口注释互相矛盾**：关于用户数据目录在 macOS 的落点，两处注释一个说「映射到 Application Support」、
    一个说「走 XDG 的 `~/.config`」。实测见第五节，前者对、后者错，按错注释做清理会找错目录。

## 六、需要你拍板的三件事

> 下面每件事都按「现在什么情况 — 不改会怎样 — 有哪些选项及代价 — 我的推荐」写全，
> 我不会替你决定，也不会在没得到答复前动手。

### 第一件：Windows 产物要不要随包带 7-Zip 程序

**现在什么情况**：Windows 的发布包里只有主程序和一个许可文件。macOS、Linux 的包里则带着仓库自带的
7-Zip 官方命令行程序，用户装完就能用。Windows 上程序会先找一个随包目录（这个目录在仓库里根本不存在），
找不到再去找系统默认路径安装的 7-Zip。也就是说，Windows 能不能压缩解压，取决于用户有没有把 7-Zip
装在那个特定位置。本机的全部测试都在 macOS 跑，碰不到 Windows 这段逻辑，所以一直没暴露。

**不改会怎样**：Windows 用户没装 7-Zip、或装在非默认目录时，除 RAR 外的所有格式都不可用，
而且报错只会说「找不到命令行程序」，不会告诉用户该装什么、装到哪。更麻烦的是我们这边会一直以为
「打包成功 = 功能可用」，因为没有任何检查能提前发现。

**选项与代价**：
- **甲：补一份官方 7-Zip 的 Windows 程序进仓库，并让发布配置复制进 Windows 包。**
  用户开箱即用，和 macOS/Linux 对齐。代价是仓库多一个二进制文件、包体积变大，
  并且需要确认该程序的再分发条款与版本来源；以后升级要单独维护一份。
- **乙：不随包带，明确「Windows 依赖预装」，把候选路径放宽（注册表、常见安装位置、
  用户自定义路径），并在找不到时给出可操作的安装提示。**
  不改产物构成、没有分发方面的顾虑。代价是用户仍需自己装一个软件。
- **丙：只补结构自检，保持现状。**
  在打包脚本里明确断言「Windows 包不含归档器，属预期」，避免以后有人误以为是漏打包。
  代价是功能缺口继续存在。

**我的推荐：乙 + 丙。** 甲能彻底解决体验，但它引入的是新的二进制资产与再分发口径，
而你之前已经明确有些第三方分发的结论不想再展开；乙用很小的改动把「依赖预装」从隐含假设变成
明确、可诊断、可提示的行为，丙则把事实写进验证链，避免我们继续被「打包成功」误导。
如果你更看重开箱即用，甲也可以做，但请先确认那份二进制的来源与再分发条款。

### 第二件：命令行 `--shutdown` 要不要真的关机

**现在什么情况**：帮助里五种语言都写着「全部完成后请求关机」，图形界面也确实会调用系统关机命令
（提前一分钟，并给一次取消机会）。但命令行走的是另一套轻量实现，只往日志写一句
「请求过关机」，不执行任何系统命令，也不报错。

**不改会怎样**：用户在脚本里加 `--shutdown` 期待跑完自动关机，结果机器一直开着，
而且从日志看还像执行过了。这是「说了会做、实际没做」的静默失效。

**选项与代价**：
- **甲：让命令行也调用真正的关机命令。** 行为与帮助一致。代价是命令行批处理会获得一个
  有系统副作用的动作，脚本误用可能直接关掉机器；且 Linux / Windows / macOS 三套命令都没在对应平台实机验证过。
- **乙：命令行显式拒绝该选项**（打印「命令行不支持自动关机，请用图形界面」并返回参数错误码），
  同时改五份帮助文本。代价是少一个功能，但行为诚实。
- **丙：加一个必须显式确认的新开关**（例如要求同时给 `--shutdown --confirm-shutdown`），
  降低误触。代价是选项变复杂，帮助与文档都要改。

**我的推荐：乙。** 自动关机会改变机器状态、且三平台命令本机验证不了，在这种条件下让命令行
「默认就能关机」风险偏高；先把行为说清楚，等以后在 Windows / Linux 实机验证过再决定要不要放开。
如果你确实需要无人值守跑完关机，选丙比甲稳妥。

### 第三件：图形界面与命令行的默认参数要不要统一

**现在什么情况**：同一个任务，两个入口的默认设置不同——界面默认「最快压缩 + 关恢复记录 + 20 GB 分卷」，
命令行默认「标准压缩 + 3% 恢复记录 + 不分卷」。用户在界面上习惯了产出一堆分卷，换到脚本里跑同一个目录，
得到的是一个整体归档，大小和恢复能力都不同。

**不改会怎样**：同一份输入在两个入口产出不同结果，用户很难判断哪个是「程序默认」，
写文档和问题排查都要先问一句「你是从哪边跑的」。

**选项与代价**：
- **甲：统一到一套默认值**（建议以现有的 `Core/Models/ArchiveDefaults.cs` 为唯一来源，两边都读它）。
  代价是**至少一边的现有行为会变**，老用户可能发现产出大小或分卷数变了，需要在版本说明里写清楚。
- **乙：保持差异，但补一张对照表并在命令行帮助里标注默认值。** 不改行为，只消除困惑。代价是要维护那张表。
- **丙：两边都改成显式要求用户选**，不再有隐含默认。代价是使用门槛上升，改动面最大。

**我的推荐：先乙、后甲分两步走。** 立刻补对照表成本几乎为零；统一默认值虽然更干净，
但它会改变已交付行为，适合放在一个单独的版本里、配一条明确的变更说明，不要和缺陷修复混在一起做。
