# v0.8.22 压缩不完整直接判失败

> 版本：`0.8.21 → 0.8.22`　模型：Claude Opus 5.5

## 用户决定

压缩时 7-Zip/RAR 返回码 1（有文件因无读权限或被占用没有写入归档），**直接算失败**。以前计为成功，用户只有看日志才会发现归档不完整。

## 改动

- 新增 `Core/Services/CompressionWarningPolicy.cs`：压缩结果 `HasWarnings` 为真时改为 `Success = false`，失败原因为“压缩不完整：<工具> 返回警告（返回码 1），有文件未写入归档，已按失败处理: <7zz/RAR 警告原文>”。
- `SevenZipArchiveEngine.CompressAsync`：创建阶段有警告就直接返回失败，不再执行校验；校验阶段返回警告也按同一规则处理。删除了 0.8.20 合并校验结果警告的代码（已用不到）。
- `RarArchiveEngine.CompressAsync`：同样套用该规则。
- 失败后走既有压缩失败回滚：删除本次生成的不完整归档；覆盖模式下恢复原来的同名归档；不删除也不移动来源。
- **解压不变**：解压时返回码 1 仍计成功，但管线不执行删除/移动归档（0.8.20 的兜底拦截保留）。

## 行为对比

| 场景 | 0.8.21 | 0.8.22 |
| --- | --- | --- |
| 压缩有文件读不了，未开后处理 | 计成功，退出码 0，留下不完整归档 | 计失败，退出码 1，不留归档 |
| 压缩有文件读不了，开删除/移动 | 计成功 + 后处理失败，来源保留 | 计失败，来源保留，不留归档 |
| 覆盖模式下已有旧归档 | 旧归档被不完整归档替换 | 旧归档恢复原样 |

终端标准错误会显示 7zz 原始警告（包括漏掉的文件路径）和“失败: <条目> - 压缩不完整……”；运行日志记录 `[ERROR] Compression failed: ...`；界面里这一项标红计失败。

## 验证

- Release 构建 0 警告 0 错误；110 项测试全部通过。回归测试场景 6 改为真实 7zz 验证：引擎返回失败且带警告原文；完整管线在覆盖 + 删除源时计失败、来源保留、旧归档恢复、输出目录只剩旧归档。
- 经验实测 43 项、端到端夹具 155 项、冒烟测试全部通过。
- 命令行实测：目录内 `ok.txt` 可读、`locked.txt` 不可读，结果 `Success=1, Failed=1`，退出码 1，输出只有 `ok.txt.7z`，`locked.txt` 保留。
- macOS 应用 0.8.22 已安装到 `/Applications`，签名校验通过，后台运行。

## 遇到时怎么处理

查看失败原因里列出的文件路径，修正读权限或关闭占用该文件的程序，然后重新压缩这一项。

## 未验证

- **Windows“文件被占用”**：Windows 上文件被其他程序独占打开时，7z 同样返回码 1，按本版规则会判“压缩不完整”失败。本轮只在 macOS 用“无读权限”验证过，这种情况还没在 Windows 真机上验证，已列入 [下一步待实现](20261121-0029-下一步待实现-Claude-Opus-5.5.md)。验证方法：用一个程序独占打开某文件（例如 PowerShell `[IO.File]::Open(路径,'Open','Read','None')`），再压缩其所在目录，确认该项计失败、退出码 1、失败原因列出该文件、来源保留。
