# 0.8.14 下一步开发详细建议（0.8.15 执行计划）

> 更新时间：2026-11-16 23:55　当前版本：`0.8.14`（.NET SDK 11.0.100 / net11.0 / Avalonia 12.1.6）
> 性质：基于 [2150 整体分析](20261116-2150-整体分析与下一步开发建议-Claude-Opus.md) 的执行细化，不改产品源码、不递增版本。
> 结论：**下一步先做 0.8.15「安全退出」**——任务执行中关窗不能硬杀进程；覆盖写入不能先删旧归档；目录大小不能跟随符号链接。依赖已经是最新（Avalonia 12.1.6、.NET 11），不需要再升。

## 一、为什么先做这一批

2150 分析里三个 P0 中，只有“关窗硬退”会直接损坏用户已有文件：

- 大批量压缩/解压时点关闭，`MainWindow_Closing` 直接释放 ViewModel，进程随最后一个窗口退出；
- 适配器的 `finally` 来不及清理附件暂存目录、来不及回滚失败输出；
- 正在写出的归档留下半成品，`rar`/`7zz` 子进程可能变成孤儿继续写盘；
- 覆盖模式下旧归档已经在 `PrepareAsync` 阶段被删除，新归档失败就新旧全失。

Windows 命令行输出、7-Zip 当前目录搜索同样重要，但它们分别需要 Windows 实机决策和额外的信任策略；安全退出可以完全在本机验证，风险最低、收益最直接。

## 二、0.8.15 目标与验收

**目标**：用户在任何时刻关闭窗口，都不会留下“看似完成、实际损坏”的归档；覆盖失败时旧归档仍在；目录大小计算不会被符号链接环路卡住。

**总验收**：

- 启动一个足够长的压缩/解压任务，点关闭 → 出现程序内确认框；
- 选择“继续执行” → 任务继续，窗口保持；
- 选择“取消任务并退出” → 任务协作式取消，等待清理，进程退出后：
  - 没有 `*.batchcompress-new-*` 临时归档；
  - 没有 `batch-compress-attachments-*` 暂存目录；
  - 没有残留 `7zz`/`rar` 子进程；
  - 日志有取消与清理记录；
- 覆盖模式用假引擎模拟“写一半失败”，旧归档字节不变；
- 符号链接环路目录的大小计算在 1 秒内结束，统计不越界；
- 现有 98 项测试、42 项实测、155 项夹具、4 条界面冒烟不回退。

## 三、任务 1：执行中关窗保护（最高优先）

### 3.1 现状与问题点

- `Views/MainWindow.axaml.cs:114` 的 `MainWindow_Closing` 只做 `SaveWindowSize()` 和 `_boundViewModel?.Dispose()`，没有 `e.Cancel`。
- `App.axaml.cs:49` 使用 `ShutdownMode.OnLastWindowClose`，关窗即退出。
- `ViewModels/OperationSession.cs:104-120` 的 `finally` 负责清理，但进程退出后不会执行。
- `MainWindowViewModel.Execution.cs:151` 已有 `CancelOperation()`，`BeginOperationCancellation`/`EndOperationCancellation` 管理令牌。
- `Views/MainWindow.axaml.cs:721` 已有 `ShowOkCancelMessageBoxAsync`，可直接复用，不需要新建对话框框架。

### 3.2 设计

**原则**：关闭请求先变成“取消 + 等待清理”，清理完成后再真正关闭；`Dispose` 必须晚于操作结束。

1. **在 ViewModel 增加“操作完成信号”**
   - `MainWindowViewModel` 用 `[ObservableProperty] private bool _isOperating;` 已有属性；
   - 增加 `TaskCompletionSource? _operationCompletion`；
   - 实现 `partial void OnIsOperatingChanged(bool value)`：
     - `true` 时创建新的 `TaskCompletionSource`（`RunContinuationsAsynchronously`）；
     - `false` 时 `TrySetResult()`；
   - 暴露 `public Task WaitForOperationCompletionAsync()`。
   - 这样关闭流程可以等待 `finally` 真正执行完，而不是只等一个布尔值。

2. **改 `MainWindow_Closing`**
   - 增加 `_closeApproved` 与 `_closeDialogOpen` 两个字段；
   - 若 `_closeApproved`：保存尺寸、`Dispose`、正常关闭；
   - 若 `_boundViewModel?.IsOperating == true`：
     - `e.Cancel = true`；
     - 异步弹出确认框（不要阻塞 UI 线程）：
       - 标题：任务正在执行
       - 正文：当前压缩/解压尚未完成，关闭会取消任务并清理临时文件，确定退出吗？
       - 确认按钮：取消任务并退出
       - 取消按钮：继续执行
     - 用户选“继续执行”：直接返回，不释放任何资源；
     - 用户确认：调用 `CancelOperationCommand.Execute(null)`，`await` 操作完成或超时（建议 10 秒）；
     - 超时：再弹一次“清理尚未完成，仍要退出吗？”；确认才强制关闭，并写崩溃/诊断日志；
     - 清理完成后设 `_closeApproved = true`，再 `Close()`；
   - 若不在执行中：保持现有 `SaveWindowSize + Dispose`。

3. **托盘退出走同一条路**
   - `App.axaml.cs` 的 `TrayExit_Clicked` 现在直接 `desktop.Shutdown()`，会绕过 `Closing` 保护；
   - 改为 `_mainWindow?.Close()`，让关窗确认生效；如果主窗口已隐藏，先显示再关闭，或直接调用同一套确认流程。

4. **避免重复弹框**
   - 关闭确认未结束时再次点关闭，直接忽略；
   - 关闭确认框的 owner 必须是可见主窗口，和「关于」窗口一样等 `Opened` 之后再 `ShowDialog`。

5. **本地化**
   - 新增 4 个五语言词条：标题、正文、确认按钮、继续按钮；
   - 超时二次确认再加 2 个词条；五份 JSON 同步，保持 0 缺失。

### 3.3 测试

- **纯逻辑测试**：新增 `CloseWhileOperatingPolicy`（不依赖 Avalonia）：
  - 不在执行中 → `CloseNow`；
  - 执行中 + 未确认 → `AskUser`；
  - 已确认 + 清理完成 → `CloseAfterCleanup`；
  - 已确认 + 超时 → `AskForceClose`；
  - 覆盖所有组合，避免以后改条件时漏分支。
- **ViewModel 信号测试**：若能把 `OperationCompletionSignal` 抽成纯类，测试 `IsOperating` 从 true→false 时 `Wait` 完成；否则用源码守护断言 `WaitForOperationCompletionAsync` 与 `OnIsOperatingChanged` 存在。
- **手工验收**：用 7z 压缩一个约 2GB 的临时目录（或人为拉长任务），关闭 → 确认 → 观察进程、临时目录、子进程；再测“继续执行”分支。

### 3.4 风险与回滚

- 风险：关窗确认改变用户习惯；等待清理可能让退出变慢。
- 回滚：只涉及 `MainWindow.axaml.cs`、`MainWindowViewModel` 的生命周期部分和新增纯策略类；回滚后恢复现有直接退出行为，不影响归档格式或数据。

## 四、任务 2：覆盖写入改成“先临时、后替换”

### 4.1 现状

`Core/Services/Pipeline/CompressionItemAdapter.cs:127-134` 在 `Overwrite` 模式下先删除所有已存在的输出卷，再调用引擎。新压缩失败时旧归档已不存在。

### 4.2 设计（分两步，先做单卷/常规，再做多卷）

**第一步：临时输出 + 成功后替换**

- `PreparedCompressionItem` 增加：
  - `FinalOutputPath`（用户期望的最终路径）；
  - `StagingOutputPath`（同目录、唯一临时名，保留正确扩展名，例如 `.<name>.batchcompress-new-<guid>.<format>`）。
- `PrepareAsync` 不再删除旧文件；只在 `Overwrite` 时记录已存在的输出卷。
- 引擎写入 `StagingOutputPath`。
- `ExecuteAsync` 成功后：
  1. 解析 staging 产生的全部卷；
  2. 把旧最终卷改名为 `.batchcompress-backup-<guid>`；
  3. 把 staging 卷按最终命名规则移动到最终路径；
  4. 删除备份；
  5. 失败则删除 staging、把备份改回原名。
- 失败/取消：删除 staging，恢复备份，保持旧归档。

**第二步：多卷与崩溃恢复（可拆到 0.8.16）**

- 多卷的 staging 卷名到最终卷名要做映射（`part1.rar`、`.001`、`.z01` 等），用 `ArchiveVolumeResolver` 已有规则；
- 进程被强杀时可能留下 `.batchcompress-backup-*` 或 staging；下次启动时：
  - 最终文件缺失且有备份 → 恢复最新备份；
  - 最终文件存在 → 删除陈旧备份与 staging；
- 这段恢复逻辑要独立成 `OutputReplacementRecovery`，不要塞进适配器。

### 4.3 测试

- 假引擎（现有测试工程有 `ScriptedArchiveEngine`）写入 staging 后返回失败：断言最终旧归档哈希不变、staging 被清理、备份被恢复。
- 假引擎成功后：断言最终文件存在、内容正确、没有残留 staging/备份。
- 多卷：至少覆盖 7z `.001` 与 RAR `part1.rar` 的命名映射；ZIP 分卷可后补。
- 现有 155 项夹具里的覆盖用例必须继续通过。

### 4.4 风险与回滚

- 风险：多卷命名映射容易出错；替换阶段崩溃仍可能留下备份。
- 回滚：把适配器恢复为“先删后写”，新增的 `OutputReplacement` 类保留但不用；不影响其它模块。

## 五、任务 3：目录大小计算排除符号链接

### 5.1 现状

`ViewModels/MainWindowViewModel.BrowsingAndFiles.cs:252` 用 `Directory.GetFiles(path, "*", SearchOption.AllDirectories)`，没有排除重解析点，也没有访问过的真实路径集合。符号链接环路可能卡住或把目录外文件算进总量。

### 5.2 设计

- 抽出 `Core/Services/DirectorySizeCalculator.cs`（纯逻辑，不引用 Avalonia）：
  - 返回 `DirectorySizeResult(long Size, IReadOnlyList<string> Errors)`；
  - 使用 `EnumerationOptions`：
    - `RecurseSubdirectories = true`
    - `IgnoreInaccessible = true`
    - `AttributesToSkip = FileAttributes.ReparsePoint | FileAttributes.System`
  - 继续用 `SystemMetadataFileFilter.ShouldSkip` 过滤元数据；
  - 对每个文件单独 `try/catch`，错误累积而不是整段失败；
- `MainWindowViewModel.UpdateTotalSizeAsync` 改成调用它；
- 把该类链接进测试工程，补：
  - 普通嵌套目录；
  - 符号链接指向父目录（macOS/Linux 用 `File.CreateSymbolicLink`，Windows 跳过）；
  - 无权限子目录（可选，避免 CI 权限差异）。

### 5.3 验收

- 环路目录在 1 秒内返回；
- 统计值不包含链接目标目录外的文件；
- 现有 ETA/总大小行为不变。

## 六、0.8.15 的提交拆分与版本

建议拆成三个独立提交，合并为一个版本 `0.8.15`：

## 八、需要你确认的只有一件事

**执行中关窗的默认行为**：

- 推荐：确认后取消任务并等待清理（本计划采用）；
- 备选：直接阻止关闭，只提示“请先取消或等待完成”；
- 不推荐：保持现在的强制退出。

如果你希望改成“阻止关闭”，第 3.2 节的确认框可以去掉，只保留提示；其余清理逻辑不变。

## 九、明确不做

- 不再升级 .NET / Avalonia：SDK 11.0.100 与 Avalonia 12.1.6 都是当前最新稳定版。
- 不做大规模重构、不引入新框架、不引入第二套配置。
- 不重新讨论 RAR 许可、macOS 签名、云端 CI 门禁。
- 不在本批顺手改 Windows 命令行方案；它需要 Windows 实机试验后再定。
