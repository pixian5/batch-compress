## 1. 批次 21（P0）全局异常兜底与崩溃日志

### 1.1 现状证据

- `Program.Main` 全文没有 `try/catch`；GUI 分支
  `BuildAvaloniaApp().StartWithClassicDesktopLifetime(...)`（`Program.cs:84`）完全裸奔。
- `App.axaml.cs` 只有托盘/状态栏帮助进程的局部 `catch`。
- 全仓库搜不到 `AppDomain.UnhandledException`、`DispatcherUnhandledException`、
  `TaskScheduler.UnobservedTaskException`。
- 无界面模式有 `RunHeadlessAsync` 的 `catch`（`Program.cs:100`），但 GUI 没有对等保护。

### 1.2 新增 `Core/Services/CrashLogService.cs`

```csharp
public static class CrashLogService
{
    private static readonly object Gate = new();
    private static DateTime _lastWriteUtc = DateTime.MinValue;
    private static string _lastSignature = string.Empty;

    public static string LogDirectory =>
        Path.Combine(AppContext.BaseDirectory, "logs");

    /// <summary>注册三类全局兜底；重复调用只注册一次。</summary>
    public static void RegisterGlobalHandlers();

    /// <summary>写一条崩溃记录；自身异常绝不外抛。</summary>
    public static void Write(string stage, Exception exception, string? context = null);

    /// <summary>写一条非异常的致命诊断（例如启动期配置损坏）。</summary>
    public static void WriteMessage(string stage, string message, string? context = null);
}
```

**写入格式**（纯文本，UTF-8，无 BOM）：

```
[2026-11-16 00:18:24.123] stage=gui-dispatcher
version=0.8.4  runtime=.NET 10.0.0  os=macOS 26.1  arch=Arm64  thread=1
exception=System.InvalidOperationException: 消息
context=压缩按钮回调
stack:
   at ...
```

**关键约束**：

1. **去重**：同一 `stage + 异常类型 + 消息前 120 字` 在 2 秒内只写一次，
   并用静态计数记录被抑制的次数，下次写入时附上 `suppressed=N`，防止异常风暴写爆磁盘。
2. **自保护**：整个 `Write` 包在 `try/catch` 里；失败退回 `Console.Error.WriteLine`，
   绝不能在兜底里再抛异常。
3. **权限**：Unix 上写完后 `File.SetUnixFileMode(path, UserRead | UserWrite)`（0600），
   与现有日志一致。
4. **容量**：`logs/` 下 `batchcompress-crash_*.log` 最多保留 20 个，超出删最旧。
5. **不写密码**：`context` 由调用方给固定短语，不拼接命令行或用户输入。

### 1.3 三处注册点

| 位置 | 事件 | 处理策略 |
| --- | --- | --- |
| `Program.Main` 第一行（参数解析前） | `AppDomain.CurrentDomain.UnhandledException` | 记录后不阻止进程退出（`IsTerminating` 为 true 时无法恢复） |
| `Program.Main` 第一行 | `TaskScheduler.UnobservedTaskException` | 记录后 `e.SetObserved()`，避免后台任务异常带走进程 |
| `App.OnFrameworkInitializationCompleted` | `Dispatcher.UIThread.UnhandledException` | 记录后 `e.Handled = true`，让界面尽量存活并提示用户查看日志 |

`Dispatcher.UIThread.UnhandledException` 若在当前 Avalonia 版本编译不通过，
降级为只注册前两个，并在报告里记录；不要为了一个事件去引额外包。

### 1.4 代码骨架

```csharp
// Program.Main
[STAThread]
public static int Main(string[] args)
{
    CrashLogService.RegisterGlobalHandlers();
    try
    {
        return RunCore(args);
    }
    catch (Exception ex)
    {
        CrashLogService.Write("main", ex, "启动或运行期未处理异常");
        Console.Error.WriteLine($"Fatal error: {ex.Message}");
        return 1;
    }
}
```

`RunHeadlessAsync` 现有 `catch` 保留，并追加一行 `CrashLogService.Write("headless", ex, ...)`。

### 1.5 测试用例

| 类型 | 用例 | 断言 |
| --- | --- | --- |
| 单元 | `Write` 生成文件 | 文件存在、含 stage/version/exception/stack、权限 0600 |
| 单元 | 2 秒内同签名写两次 | 只生成一条记录，含 `suppressed=1` |
| 单元 | `Write` 传入会抛异常的上下文 | 不向外抛，退回控制台 |
| 单元 | 生成 25 个文件 | 只保留 20 个，最旧被删 |
| 手工 | 界面按钮回调临时 `throw` | 应用不消失，日志有完整堆栈，界面给出「查看日志」提示 |
| 手工 | 后台任务不 await 抛异常 | 进程不退出，日志有记录 |

### 1.6 验收与风险

- 风险：兜底处理器里不要弹模态框、不要等锁；`File.SetUnixFileMode` 在 Windows 上要跳过。
- 版本：`+0.0.1` → `0.8.5`。

## 2. 批次 22（P1）日志与报告容量上限、节流刷新

### 2.1 现状证据

- `MainWindowViewModel.cs:436-452`：`_sourceFileList`、`_successLog`、`_failLog`、`_commandLog`
  都是 `[ObservableProperty] string`。
- `CommandLog +=` 共 **31 处**，`SuccessLog +=` / `FailLog +=` 各 1 处；
  每次追加都复制整段字符串并触发一次全量属性通知。
- 全仓库无 `MaxLog` / `Truncate` / `TakeLast`。
- `BatchReportCollector` 的 `List<BatchReportEntry>` 无上限。

### 2.2 新增 `ViewModels/LogBuffer.cs`

```csharp
public sealed class LogBuffer
{
    public LogBuffer(int maxLines = 5000, int flushIntervalMs = 200);

    public int MaxLines { get; }
    public int OmittedCount { get; private set; }
    public bool IsDirty { get; private set; }

    /// <summary>追加一段文本（可含换行），按行入队并裁剪最旧行。</summary>
    public void Append(string text);

    /// <summary>到刷新间隔返回 true，并给出当前完整文本。</summary>
    public bool TryFlush(out string text);

    /// <summary>无条件刷新（批次结束、清空、导出前调用）。</summary>
    public string Flush();

    public void Clear();
}
```

内部结构：`Queue<string> _lines` + `int _omitted` + `long _lastFlushTicks`。
超出上限时 `Dequeue` 并 `_omitted++`；`BuildText` 在开头插入一行
`（已省略最早的 N 行）`，N 为 0 时不插入。

### 2.3 ViewModel 改造

```csharp
private readonly LogBuffer _commandLogBuffer = new();
private readonly LogBuffer _successLogBuffer = new();
private readonly LogBuffer _failLogBuffer = new();

private void AppendCommandLog(string text)
{
    _commandLogBuffer.Append(text);
    if (_commandLogBuffer.TryFlush(out var snapshot)) CommandLog = snapshot;
}

private void AppendSuccessLog(string text) { /* 同上 */ }
private void AppendFailLog(string text) { /* 同上 */ }

private void ForceFlushLogs()
{
    CommandLog = _commandLogBuffer.Flush();
    SuccessLog = _successLogBuffer.Flush();
    FailLog = _failLogBuffer.Flush();
}
```

替换规则：

1. `CommandLog += X;` → `AppendCommandLog(X);`（31 处）
2. `SuccessLog += X;` / `FailLog += X;` → 对应方法（各 1 处）
3. **不要动** `SourceFileList`：它是源清单而非日志，且由选择/导入逻辑整体赋值。
4. 清空命令改为 `_commandLogBuffer.Clear(); CommandLog = string.Empty;`。
5. 批次结束、窗口关闭、导出报告/诊断前调用 `ForceFlushLogs()`。

节流是「按时间判断」而不是定时器，避免引入 `DispatcherTimer` 生命周期问题：
`TryFlush` 内部比较 `Environment.TickCount64`，未到 200 毫秒返回 false；
调用方每次追加都会尝试，到点才更新绑定。

### 2.4 报告收集器上限

```csharp
public sealed class BatchReportCollector
{
    public const int MaxEntries = 20_000;
    public int OmittedEntries { get; private set; }
    // Report 内：达到上限后 _omitted++，不再 Add
}
```

`BatchReportWriter.ToMarkdown` 末尾追加：
`另有 N 条因超出上限未列出，请缩小批次或分批执行。`
CSV 末尾追加一行同义说明（首列留空，避免破坏表结构）。

### 2.5 测试用例

| 用例 | 断言 |
| --- | --- |
| 追加 6,000 行（上限 5,000） | 文本含 5,000 行 + 「已省略最早的 1,000 行」 |
| 200 毫秒内连续追加 100 次 | `TryFlush` 只有第一次（或到点那次）返回 true |
| `Clear` 后 | 文本为空、省略计数归零 |
| 报告 20,001 条 | `Entries.Count == 20,000`，`OmittedEntries == 1`，Markdown 含省略提示 |
| 一万条模拟 | 内存与刷新耗时有界（手工观察，不做精确基准） |

### 2.6 验收与风险

- 验收：现有 74 项测试零回归；`grep -c "CommandLog +="` 为 0；
  一万条任务界面可滚动、清空正常、报告与诊断导出正常。
- 风险：节流导致最后几行延迟，必须在批次结束强制刷新；
  上限只控制容量，不得改变「命令日志含密码不脱敏」的内容策略。
- 版本：`+0.0.1`。
