# v0.8.20 归档警告保留来源修复

> 时间：2026-11-20 23:35　版本：`0.8.19 → 0.8.20`　模型：Claude Opus 5.5

## 问题

7-Zip 和 RAR 的返回码 1 表示“非致命警告”，例如有文件因无读权限没被压进归档。项目把 0 和 1 都当成功，成功后执行“删除源/移动源”。实测：不可读文件生成 158 字节的空归档，`7zz t` 校验仍然通过，源文件被删除。分析见 [整体分析与数据丢失缺陷](20261120-2327-整体分析与数据丢失缺陷-Claude-Opus-5.5.md)。

## 改动

- `Core/Interfaces/IArchiveEngine.cs`：`ArchiveResult` 新增 `HasWarnings`。
- `Core/Services/SevenZipArchiveEngine.cs`、`RarArchiveEngine.cs`：返回码 1 时 `HasWarnings = true`；7zz 创建后再校验时，创建阶段的警告和返回码合并进最终结果，不会被校验结果覆盖。
- `SevenZipCommandBuilder.cs`、`WinRarCommandBuilder.cs`：新增常量 `Warning = 1`。
- `Core/Services/Pipeline/BatchExecutionPipeline.cs`：串行与并发两条路径统一走 `ApplyPostProcess`。有警告时写警告日志；开启删除/移动时跳过后处理，记一条后处理失败。界面显示“成功但后处理失败”，命令行退出码为 1。
- 五语言新增词条 `PostProcessSkippedArchiveWarning`。
- 新增回归测试 `BatchCompress.Avalonia.Tests/Program.ArchiveWarningTests.cs`：压缩删除源（串行、并发）、压缩移动源、解压删除归档、无后处理、真实 7zz 无读权限文件，共 6 个场景。
- 仓库卫生：`批量压缩解压.csproj.user` 移出 Git 跟踪（`.gitignore` 早已忽略 `*.user`）。

## 行为变化

- 有警告且未开启后处理：条目仍计成功，只写警告日志，命令行退出码不变。
- 有警告且开启删除/移动：来源保留，`PostProcessFailed` 加 1，命令行退出码 1。
