# 整体分析与下一步开发建议（0.8.4）

> 用户原问题：「整体分析项目，给出下一步开发详细建议」
>
> 撰写时间：2026-11-16 00:15　模型：Claude-Opus　基准版本：`VERSION 0.8.4`
> 方法：实读当前源码、测试工程、打包脚本与 `docs/`、`经验/`，并跑了依赖过期检查与代码风险扫描；
> 未启动图形界面、未改动产品源码，`VERSION` 保持 `0.8.4`。
> 按用户 2026-11-15 的决定，本文不再涉及签名公证、RAR 许可与云端 Actions。

## 一、结论摘要

项目已经完成了一个相当完整的闭环：**功能项全部交付、测试四层齐全、本机打包运行正常**。
代码扫描结果很干净——没有 TODO/FIXME，没有 `async void`、`.Result`/`.Wait()` 阻塞，
没有硬编码用户目录，只有 1 处空 `catch`（读版本文件的兜底，合理）。

所以下一步不该再「加功能」，而是**补稳定性与长期可维护性的短板**。按影响排序：

1. **没有全局异常兜底**：界面线程、后台任务、未观察任务异常都没有统一捕获，
   崩溃时应用可能直接消失，日志里也不会留下堆栈。这是本地应用最该补的一块。
2. **界面日志是纯字符串无上限追加**：`_commandLog` 等每次 `+=` 都复制整段文本并触发全量刷新，
   大批量任务下是 O(n²) 开销，且内存只增不减。
3. **依赖有可用更新**：Avalonia 12.1.5 → 12.1.6（补丁，风险低）；
   日志库 10.0.14 → 11.0.0（主版本，需单独评估）。
4. **本地化字典仍是 1,752 行硬编码**：加一种语言或改一个词条的成本仍偏高。
5. **界面交互没有自动化回归**：仓库里只有点击/截屏的底层小工具，没有可复跑的交互用例。

建议顺序：**P0 稳定性 → P1 性能与补丁 → P2 可维护性 → P3 体验**。

## 三、问题清单（按影响排序）

### D1（P0）没有全局异常兜底，崩溃后无法定位

**证据**：`App.axaml.cs` 只有托盘/退出相关的局部 `catch`；
`Program.cs` 的 `Main` 没有 `try/catch`；全仓库搜不到
`AppDomain.UnhandledException`、`DispatcherUnhandledException`、`TaskScheduler.UnobservedTaskException`。

**影响**：界面线程抛异常时应用可能直接退出，日志文件里只留到崩溃前最后一条业务日志，
没有异常类型、消息和堆栈。对一个强调「增加详细日志帮助发现问题」的本地应用，这是最明显的缺口。

**建议**：在 `Program.Main` 里注册三类兜底，并写入现有日志文件：

- `AppDomain.CurrentDomain.UnhandledException`（进程级，无法恢复，但必须留证据）；
- `TaskScheduler.UnobservedTaskException`（后台任务异常）；
- Avalonia 的 `DispatcherUnhandledException`（界面线程，可选择记录后标记已处理，避免直接消失）。

日志内容至少包含：时间、线程、异常类型、消息、完整堆栈、当前版本、操作阶段。
同时给用户一个可操作的提示（日志路径 + 导出诊断入口）。

### D2（P1）界面日志无上限且是 O(n²) 追加

**证据**：`MainWindowViewModel.cs:436-452` 的 `_sourceFileList` / `_successLog` / `_failLog` /
`_commandLog` 都是 `[ObservableProperty] string`；全仓库搜不到 `MaxLog` / `Truncate` / `TakeLast` 之类的上限逻辑。
绑定到界面的 `TextBox` 每次都会重新接收整段文本。

**影响**：一批一万个任务时，每追加一行都要复制整段字符串并触发一次全文刷新，
总复制量随行数平方增长；同时内存只增不减。表现为批处理越到后面界面越卡、内存持续上涨。

**建议**（按侵入度从低到高，选其一）：

1. **低侵入**：每类日志设行数上限（例如 5,000 行），超出时丢弃最旧行并在日志顶部留一行「已省略 N 行」；
2. **中侵入**：追加改到 `StringBuilder`，用 200 毫秒节流合并刷新（`DispatcherTimer` 或时间戳判断），
   只在空闲时更新绑定属性；
3. **大改**：日志区换成虚拟化列表（`ListBox` + `ObservableCollection`），
   但会牵动界面布局与现有「清空某类日志」逻辑，不建议与稳定性批次混在一起做。

无论选哪种，都要保留「命令日志含密码不脱敏」的既定行为，只做容量控制，不做内容裁剪。

### D3（P1）Avalonia 有补丁更新

**证据**：`dotnet list package --outdated` 显示四个 Avalonia 包都有 `12.1.5 → 12.1.6`。

**影响**：补丁通常修渲染/输入/平台兼容问题；不升级不会立刻坏事，但会错过修复。

**建议**：四个包一起升到 12.1.6，按本机验证流程跑一遍（构建、74 项测试、21 项实测、
149 项夹具、打包运行）。这是低风险改动，适合单独一个小批次。

### D4（P2）日志库 11.0.0 是主版本，需单独评估

**证据**：`Microsoft.Extensions.Logging`、`.Console`、`System.Resources.Extensions`
均有 `10.0.14 → 11.0.0`。

**影响**：主版本可能有 API 变化或行为差异；与 Avalonia 补丁混做会把风险叠加。

**建议**：单独一批，先读 11.0 的破坏性变更说明，升级后重点验证日志格式、轮转、
0600 权限与诊断导出；有问题就回退，不与其它改动混在一起。

### D5（P2）本地化字典 1,752 行仍是硬编码

**证据**：`LocalizationService.cs` 里五套语言各一个约 290 行的 `Create*()` 方法；
`LanguageStrings.cs` 是 364 行属性类。批次 14 只把命令行帮助拆到了 `HelpTexts.cs`，
界面词条仍在同一个大文件里。

**影响**：加一种语言要改 3 处（属性、字典、可用语言列表）并新增约 290 行；
改一个词条要在 5 个方法里找同样的键，容易漏。

**建议**：外置为 `.resx` 或 JSON 资源（项目已引用 `System.Resources.Extensions`），
`LocalizationService` 改为按语言加载；先用现有「界面本地化资源扫描」测试锁住键集合，
再迁移，保证零漂移。这是一次纯重构，风险主要在漏键，测试能兜住。

### D6（P2）主窗口代码隐藏 789 行

**证据**：`Views/MainWindow.axaml.cs` 789 行，包含拖放、快捷键、窗口状态、缩放等。

**影响**：MVVM 边界被稀释，界面逻辑难以单测；与 854 行的 ViewModel 形成两套状态来源。

**建议**：把可下沉的逻辑（缩放、窗口状态、部分拖放解析）移到 ViewModel 或独立服务，
代码隐藏只保留纯视图事件转发。与 D5 分开批次做，避免一次改太多。

### D7（P2）界面交互没有自动化回归

**证据**：`测试夹具/` 下只有 `gui-click.swift`（按坐标点击）与 `gui-screen.swift`（读屏幕尺寸），
没有可复跑的界面用例；现有 149 项夹具全部走命令行。

**影响**：界面按钮、导出、语言切换、进度条这类改动只能靠人工点，回归成本高。

**建议**：不追求完整 GUI 测试框架，先做 3 条「冒烟级」用例：
启动后窗口存在、切一次语言后标题变化、跑一个最小压缩任务并确认成功计数为 1。
可用现有的点击/截屏工具拼一个脚本，产物放 `测试夹具/界面冒烟/`，不进任何云端流程。

### D8（P3）报告收集器无上限

**证据**：`BatchReportCollector` 用 `List<BatchReportEntry>` 累积，没有容量限制；
每次会话新建，单次会话内只增不减。

**影响**：几万条任务时约占几 MB，通常可接受；但与 D2 同批做「上限」改造更省事。

**建议**：与 D2 一起加统一上限（例如最多保留 20,000 条，超出只累计计数并标注「已省略」）。

### D9（P3）缺少「关于」入口

**证据**：全仓库搜不到「关于 / About」对话框；版本只在窗口标题里跟随程序集显示。

**影响**：本地排障时用户不容易一次拿到「版本 + 运行时 + 日志路径 + 诊断导出入口」。

**建议**：主界面加一个轻量「关于」弹窗（版本、.NET 版本、日志目录、诊断导出按钮、结果报告目录），
五语言文案补齐。这是体验项，不紧急。

## 六、一句话总结

**功能已经够用，接下来值钱的是「崩了能查、跑久了不卡、加语言不难、界面能回归」。**
优先做前三项，其余按需。
