# 整体分析与下一步开发建议（0.8.13）

> 分析时间：2026-11-16 21:50　版本：`0.8.13`　分支：`main`
> 性质：**只读分析**，不改产品源码、不递增版本。结论基于当前源码、打包脚本、真实打包应用与测试记录。
> 一句话结论：四批缺陷修完后，项目已经进入“功能基本齐、边界要压实”的阶段；下一步最该做的是**防止运行中丢数据、把 Windows 命令行交付做实、统一安全边界**，而不是继续加功能或大重构。

## 一、总体判断

这个项目现在的主线是清楚的：一个跨平台批量压缩解压桌面工具，图形界面与命令行双入口，压缩/解压交给外部 `rar` / `7zz`，自己负责编排、进度、日志、报告、诊断与打包。

`0.8.13` 的质量状态是本项目历史上最好的一档：

- 98 项单元测试、42 项经验实测、155 项端到端夹具、4 条界面冒烟、交付冒烟全过。
- Debug / Release 构建均 0 警告 0 错误。
- GitHub 上的三平台 CI 最近 5 次全部成功（Windows / macOS / Linux 都能构建并通过现有测试）。
- 版本号、路径口径、诊断脱敏、日志权限、夹具断言这些“以前踩过坑”的地方，已经收口得比较干净。

但这次审查仍然发现了几个**会直接影响用户数据或功能承诺**的问题，集中在三处：

1. **运行中关窗会直接退出进程**，取消/回滚逻辑来不及执行，可能留下半个归档、附件暂存目录和孤儿压缩进程。
2. **Windows 产物是图形子系统程序**，从命令提示符运行时看不到任何命令行输出，“完整命令行入口”在 Windows 上实际不成立。
3. **7-Zip 查找包含“当前工作目录”**，用户在不受信任的目录里运行命令行时，可能执行到伪装成 `7zz` 的程序。

另外还有几处“承诺与事实不一致”：界面叫“随机密码”但密码是按文件名算出来的固定值；打包后的诊断包版本显示 `unknown`；README 说 Linux 不携带 RAR，实际构建会整包复制。下面逐项展开。

## 二、项目现状地图

### 2.1 入口与分层

```text
Program.Main
├─ 帮助 / 版本 / 参数错误：不初始化 Avalonia，直接返回
├─ 命令行：HeadlessBatchRunner
│    └─ BatchOperationService → BatchExecutionPipeline → 条目适配器 → ArchiveEngineRouter
│         ├─ RarArchiveEngine（rar / WinRAR）
│         └─ SevenZipArchiveEngine（7zz / 7z.exe）
└─ 图形界面：MainWindowViewModel
     └─ OperationSession → 同一个 BatchOperationService / Pipeline
```

支撑层：

- `Core/Models`：格式能力目录、默认参数、操作模型。
- `Core/Services`：引擎、命令构建、进程边界、卷解析、密码、来源收集、日志、报告、诊断、崩溃日志、系统通知、关机、7-Zip 自动安装。
- `Localization`：五份 JSON 资源 + `LanguageStrings` 属性 + 加载器。
- `Views` / `ViewModels`：唯一主窗口、「关于」窗口、页签状态、日志缓冲。
- `scripts`：三平台打包、全量冒烟；`测试夹具`：经验实测、端到端、界面冒烟。

分层总体是健康的：界面不直接拼归档命令；引擎不依赖 Avalonia；命令行与界面共用批处理服务。`MainWindowViewModel` 仍有 900 行左右，但已经拆成多个 partial，短期不需要大动。

### 2.3 交付与外部状态

- 版本唯一来源是根目录 `VERSION`，csproj、程序集信息、`--version`、macOS `Info.plist`、打包产物命名都读它。
- 三平台 CI 目前是绿的，但按你的既定决定，**它不作为交付门禁**；本机验证仍然是交付依据。
- macOS 使用临时签名，不做正式签名与公证（既定决定）。
- Windows 不随包带 7-Zip，首次真实执行时自动下载到 `%LOCALAPPDATA%\BatchCompress\7zip`（既定决定）。
- Linux 默认随包携带官方完整 RAR 分发包（`tools/rarLinux`），可用 `--no-rar` 剥离；RAR 许可结论按既定决定不处理。

## 三、已经做好的部分（不要在下一步推翻）

- **密码脱敏**：诊断包对 `-p` / `-hp` / `--password` 的常规、等号、冒号、引号整体形态都能替换；报告与结构化输出整条排除命令原文。
- **日志安全**：Unix 日志文件创建即 0600；崩溃日志先建空文件收紧权限再写；轮转与 gzip 归档保留权限。
- **夹具可信度**：文件缺失不再判通过，`Skipped` 改精确值，zip/rar 增加产物与 SHA-256 内容校验。
- **命令行一致性**：缺失来源逐项计数、尾斜杠文件可用、运行器文案五语言、显式 `--lang` 启动生效。
- **界面生命周期**：语言事件可退订、文件日志器可释放、串行进度快照克隆、页签显隐通知齐全、日志有一次性的尾刷。
- **默认参数唯一来源**：`ArchiveDefaults` 同时服务界面字段、页签状态、命令行与兜底值。

## 四、问题清单（按风险排序）

> 风险口径：**P0** = 可能造成数据损坏、代码执行或核心功能承诺不成立；**P1** = 跨平台明显缺陷或用户会被误导；**P2** = 质量、可维护性、边界加固；**P3** = 文档与仓库卫生。

### P0-1 运行中关闭窗口会直接杀进程

**证据**：`Views/MainWindow.axaml.cs:114` 的 `MainWindow_Closing` 只保存窗口尺寸并 `Dispose`，没有检查 `IsOperating`、没有 `e.Cancel`；`App.axaml.cs:49` 使用 `ShutdownMode.OnLastWindowClose`。

**影响**：用户在大批量压缩/解压时点关闭，进程立即退出：

- 适配器的 `finally`（附件暂存目录清理、失败回滚）来不及执行；
- 正在写出的归档留下半成品或多卷残片；
- 已启动的 `rar` / `7zz` 子进程可能变成孤儿进程继续写盘；
- 日志器被释放后，即使进程没有立刻退出，后续日志也会静默丢失。

**建议**：窗口关闭时若 `IsOperating` 为真，默认**不直接退出**：

1. 弹出程序内确认框，说明“当前任务正在执行，关闭会取消并清理”；
2. 用户确认后触发协作式取消，等待 `OperationSession` 的 `finally` 完成（设一个上限，例如 10 秒）；
3. 清理完成后再真正关闭；超时才强制结束，并写一条崩溃/诊断日志；
4. `Dispose` 延迟到操作结束之后，避免日志器提前释放。

这是下一步最该先做的一项。

### P0-2 Windows 命令行输出不可见

**证据**：`BatchCompress.Avalonia.csproj:4` 是 `<OutputType>WinExe</OutputType>`。Windows 上这是图形子系统程序，从 `cmd.exe` / PowerShell 启动时不会附加控制台，`Console.WriteLine` 没有可见去处；现有 CI 只跑测试工程，不跑打包后的 exe，所以发现不了。

**影响**：Windows 用户执行 `BatchCompress.Avalonia.exe --help`、`--version`、`compress ...` 时看不到帮助、进度、错误；重定向到文件也可能拿不到内容。命令行自动化在 Windows 上等于不可用。

**建议**：三选一，需要你拍板（见第六节）：

- 拆成两个可执行文件：图形界面用 `WinExe`，命令行用普通 `Exe`，共用同一个类库；
- 单个普通 `Exe`，启动图形界面时用系统调用隐藏控制台窗口（从资源管理器启动会闪一下）；
- 保持 `WinExe`，命令行模式下附加父进程控制台（`AttachConsole`），但重定向与无控制台场景仍需实测。

无论选哪条，都要在 Windows 上做一次“从 cmd 运行并重定向到文件”的实测，并把结果写进交付说明。

### P0-3 7-Zip 查找会执行当前目录里的程序

**证据**：`Core/Services/SevenZipArchiveEngine.cs:157` 与 `:167` 把 `Directory.GetCurrentDirectory()/tools/7zip/.../7zz` 作为候选；`TryValidateExecutable` 会给它补执行位并运行 `7zz i` 做身份校验。

**影响**：用户在下载来的项目目录、临时目录或任何可写目录里运行命令行时，如果该目录里放了伪造的 `tools/7zip/macos/7zz` 或 `tools/7zip/linux-x64/7zz`，程序会以当前用户身份执行它。这是典型的“不受信任搜索路径”问题，桌面应用和命令行都可能中招。

**建议**：

- 生产路径只信任 `AppContext.BaseDirectory` 与系统安装位置；
- 开发调试需要当前目录查找时，用显式环境变量（例如 `BATCHCOMPRESS_7ZZ_PATH`）或调试开关，并在日志里写“使用了显式指定的程序”；
- 加一个回归测试：把工作目录切到含伪造程序的临时目录，断言不会被选中；显式指定路径时才允许。

### P1-1 “随机密码”其实是按文件名算出的固定密码

**证据**：`Core/Services/PasswordUtility.cs:113` 的 `GenerateCompressionPassword` 用 `MD5UTF878(文件名 + 固定字符串)` 拼出密码；界面词条 `RandomPassword` 是“随机密码”，提示文字才写“按文件名生成”。

**影响**：知道归档文件名的人可以离线算出密码。归档文件本身通常就带文件名，所以这类“加密”对拿到文件的人几乎没有保护作用。用户可能把“随机密码”理解成密码学随机，产生错误的安全预期。

**建议**：

- 短期（低风险）：把界面标签、命令行帮助、README 统一改成“按文件名生成密码”，并明确说明“用于兼容旧版，不是密码学保护”；
- 中期（可选）：增加一个真正的密码学安全随机模式（使用系统随机数生成器，长度足够），作为显式选项，不静默改变默认值，因为默认值一变，旧归档密码查询就对不上；
- 不要直接改现有派生算法，否则历史归档无法再生成同一密码。

### P1-2 打包应用的诊断包版本是 `unknown`

**证据**：`Core/Services/DiagnosticsExportService.cs:229` 从程序目录向上找 `VERSION` 文件；三个打包脚本都只复制可执行文件、许可证和工具，不复制 `VERSION`。实测打包后的 `v0.8.13` 导出诊断包：

```json
"AppVersion": "unknown"
```

**影响**：用户发来的诊断包无法确认是哪个版本，排查时容易对错代码；也与“关于”弹窗、`--version` 的口径不一致。

**建议**：诊断摘要直接调用 `ApplicationInfoService.ReadApplicationVersion()`（读程序集信息版本，和 `--version` 同源），删掉自己扫 `VERSION` 文件的逻辑；加一条测试：临时目录里没有 `VERSION` 时仍返回正确版本。

### P1-3 Linux 关机命令大概率对普通用户失败

**证据**：`Core/Services/SystemPowerService.cs:41` 使用 `"shutdown"`（依赖 PATH），参数 `-h +1`；多数 systemd 发行版的 `/sbin` 不在普通用户 PATH 中，且关机动作需要 root 或 polkit 授权。

**影响**：Linux 上“完成后关机”可能报“找不到命令”或“需要交互式认证”，命令行只打印一条失败警告；功能在 Linux 上名义存在、实际不可用。

**建议**：

- 先按绝对路径查找 `/usr/sbin/shutdown`、`/sbin/shutdown`；
- 失败时给出可操作提示（需要 root、polkit 或使用 `systemctl poweroff`），不要只说“关机失败”；
- 在 Debian 13 上用普通用户和 root 各实测一次，把结论写进平台说明；
- 如果确认普通用户无法可靠关机，就把 Linux 标注为“需要相应权限”，不要继续承诺无条件可用。

### P1-4 命令行文本清单里的缺失项被静默跳过

**证据**：`HeadlessBatchRunner.cs:448` 使用 `LoadFilesFromTextFile`，它只返回存在的条目；`LoadFilesFromTextFileWithDiagnostics` 才会把缺失、分卷不完整、大小写歧义放进诊断结果。界面 `MainWindowViewModel.BrowsingAndFiles.cs:104` 用的是带诊断版本并会提示，命令行不用。

**影响**：同一份 TXT 清单，界面会告诉用户“有 3 个找不到”，命令行却可能只处理找到的几项并返回成功（或因为空清单返回 1），自动化脚本无法知道有缺失。与 0.8.13 刚统一的“缺失项逐项计数”口径不一致。

**建议**：命令行改用带诊断的加载方法：

- 把缺失条目补成 `FileEntry`，交给适配器按“未找到”计数；
- 或者至少把诊断结果逐条写到标准错误，并在摘要里体现；
- 试运行时也要能列出这些缺失项；
- 加一条实测：一个存在的归档 + 一个不存在的清单项，退出码 0、`NotFound=1`、存在项正常产出。

### P1-5 README 对 Linux RAR 的描述与构建事实不符

**证据**：

- `README.md:144` 说“发布产物只携带官方 7zz，不打包任何第三方 RAR/WinRAR”；
- `README.md:151` 说“当前构建不会把它复制到输出目录，运行时不依赖它”；
- `BatchCompress.Avalonia.csproj:47-51` 在 Linux x64 条件下复制 `tools/rarLinux/**`；
- `scripts/package-linux.sh` 还专门校验 `tools/rarLinux/rar`、`unrar`、`license.txt`，默认打包，只有 `--no-rar` 才剥离。

**影响**：公开文档与真实产物矛盾；用户、审核者、未来的维护者都会被误导。这不是要重新讨论 RAR 许可决策（你已明确不处理），而是**文档必须说真话**。

**建议**：把 README 改成“Linux x64 默认携带官方完整 RAR 分发包，可用 `--no-rar` 生成不携带版本；macOS 默认不注入，Windows 依赖系统安装”；同时保留现有许可风险说明的链接。不要在没有新决策的情况下改打包行为。

### P1-6 Windows 命令行默认日志落在程序目录

**证据**：`ApplicationInfoService.ResolveCliLogDirectory()` 返回 `AppContext.BaseDirectory/logs`；界面日志在用户数据目录。Windows 用户若把程序放在 `Program Files` 或只读目录，`FileLoggerService` 创建日志失败，只打印一条控制台警告（而 Windows 命令行输出本身还可能不可见），诊断包也就没有日志。

**影响**：Windows 上命令行排查信息丢失；用户以为“没有日志”其实是没权限。

**建议**：命令行默认日志改到用户数据目录（例如 `%LOCALAPPDATA%\BatchCompress\logs`），`--log-file` 仍可显式覆盖；同步更新“关于”与 README 的路径口径，并加路径单元测试。这是行为变化，但对用户更安全。

### P1-7 7-Zip 自动安装失败后不会重试

**证据**：`ViewModels/MainWindowViewModel.Tooling.cs:17` 用 `_archiveToolingTask ??= ...` 缓存任务；第一次因断网/代理失败后，任务结果一直保留，用户再点压缩也不会重新尝试，只能重启应用。

**影响**：临时网络故障被放大成“本次运行永久不可用”；用户不知道为什么第二次仍然失败。

**建议**：失败时把缓存的 task 清空，下一次操作重新尝试；可加简单的退避（例如 30 秒内不重复下载）和“重试”提示。命令行侧每次进程启动本来就会重试，不受影响。

### P1-8 覆盖模式先删除旧归档，再创建新归档

**证据**：`Core/Services/Pipeline/CompressionItemAdapter.cs:127-134` 在 `ExistingFileMode.Overwrite` 下先删除已存在的输出文件（含多卷全组），然后才调用引擎。

**影响**：如果新压缩失败（磁盘满、密码错误、外部程序崩溃），旧归档已经被删，用户同时失去新旧两份。覆盖是用户选择的语义，但“失败后旧文件也没了”通常不是用户预期。

**建议**：先写到同目录的临时名字（或临时卷组），成功并校验通过后再原子替换；多卷场景先把旧卷改名为 `.bak`，成功后删除，失败则恢复。加一个“假引擎写一半失败”的回归测试，断言旧归档仍在。

### P2-1 目录大小计算可能跟随符号链接

**证据**：`ViewModels/MainWindowViewModel.BrowsingAndFiles.cs:252` 使用 `Directory.GetFiles(path, "*", SearchOption.AllDirectories)`，没有排除重解析点，也没有访问过的真实路径集合。

**影响**：目录里有指向父目录的符号链接时，可能循环枚举、长时间卡住或把目录外文件算进总量；遇到无权限子目录会整段失败，只留下一条错误。

**建议**：抽成独立的 `DirectorySizeCalculator`，使用 `EnumerationOptions` 排除 `ReparsePoint`，`IgnoreInaccessible = true`，按目录收集错误；加符号链接环路测试。抽出来后也顺便解决“界面纯逻辑无法单测”的问题。

### P2-2 报告与结构化输出的密码兜底规则没有跟上诊断包

**证据**：`Core/Services/BatchReportService.cs:203` 的 `CredentialPattern` 要求 `-p` 前是行首或空白；引号包住整个参数的 `"-pSuper Secret 123"` 不匹配。`NdjsonOutputWriter` 只排除 `IsCommandOutput`，对普通 `message` 不做脱敏。

**影响**：目前命令原文整条被排除，所以不是立刻可利用的漏洞；但这是“第二道保证”，一旦将来有引擎把命令文本塞进错误消息，报告或 JSON 流就可能带出密码。

**建议**：把诊断包里的脱敏逻辑抽成共享的 `CredentialRedactor`，报告消息与 NDJSON 的 `message` 都过一遍；保留“命令输出整条排除”的第一道保证；补引号形态与普通路径不误伤的测试。

### P2-3 界面通知里还有硬编码中文

**证据**：`Core/Services/SystemIntegrationService.cs` 的 `CancelShutdownAsync` 在失败时调用 `ShowNotification("操作失败", "取消关机失败，可能没有待取消的关机请求。")`，不跟随语言。

**影响**：德语/日语等界面在取消关机失败时突然出现中文；属于局部文案回退。

**建议**：补两个五语言词条，或复用已有的通知标题/失败文案。

### P2-4 结果报告写入不是原子的

**证据**：`Core/Services/BatchReportService.cs:322` 直接 `File.WriteAllText(fullPath, content, ...)`。

**影响**：写报告时进程被杀/磁盘满，会留下半截 CSV/Markdown；用户可能把它当成完整结果。

**建议**：同目录临时文件 + 原子替换，和日志轮转的做法一致；失败时保留原报告并记录错误。

### P2-5 格式能力目录里有“已声明但未实测”的组合

**证据**：`Core/Models/ArchiveFormatCatalog.cs` 给 `gz`、`bz2`、`xz`、`tar` 标了 `SupportsVolumes = true`，但 155 项夹具的分卷只覆盖 7z、ZIP、RAR、TAR；GZ/BZ2/XZ 的分卷往返没有实测。

**影响**：界面/命令行可能允许用户创建这些格式的分卷，但解压行为没有验证；属于“配置声明超过实测覆盖”。

**建议**：要么补三种格式的分卷创建+解压往返，要么把未验证的 `SupportsVolumes` 改为 false，并在格式说明里写清。不要靠推断。

### P2-6 界面纯逻辑仍然大多不可单测

**证据**：测试工程没有链接 18 个生产文件，包括 `MainWindowViewModel` 的多个 partial、`OperationSession`、`SystemIntegrationService`、`Views`、`App`、`Program`。目录大小、文本导入展示、ETA 估算、页签状态迁移等纯逻辑仍在界面文件里。

**影响**：过去“页签显隐、串行进度串台”这类问题只能靠人工点界面发现；0.8.13 只抽出了 `TabVisibility` 一个纯类。

**建议**：按“无 Avalonia 依赖”的标准逐步抽：

1. `DirectorySizeCalculator`（见 P2-1）；
2. 文本清单导入结果的展示文本（`TextImportPresenter`）；
3. `OperationSession` 的 ETA/速度计算（`ProgressEstimator`）；
4. `OperationTabState` 的保存/恢复迁移；
5. 抽一个就链接进测试工程并补测试，不要一次性大搬。

### P2-7 窗口状态恢复没有边界校验

**证据**：`Core/Services/WindowStateService.cs` 直接使用保存的宽高与坐标，没有最小尺寸、屏幕可见区域或负数校验。

**影响**：换显示器、缩放变化或文件被手工改坏后，窗口可能恢复到屏幕外或小到无法操作。

**建议**：恢复时按当前屏幕工作区夹取，设置最小宽高；加载失败已有兜底，保持。

### P3-1 文档数量大、历史口径多，容易误读

**证据**：`docs/` 已有 135 个 Markdown，`文档索引.md` 158 行；根目录另有 640 行的 `压缩.md`、666 行的 `解压.md`，最后更新是 2026-09-30，未被索引引用，内容停在 2026-08-10 的代码状态。

**影响**：新维护者或未来的模型很容易把历史文档当成现状，重复 0.8.11 分析里已经纠正过的误报。

**建议**：

- 在 README 固定一块“当前事实”（版本、验证基线、平台限制、唯一入口），所有判断先看这里；
- 旧文档不删，移到 `docs/archive/` 或加“已过时，以 XX 文档为准”的顶部横幅；
- 根目录 `压缩.md` / `解压.md` 要么移入 `docs/` 并标注日期，要么明确标为历史；
- 索引按“当前 / 历史”分组，而不是只有时间倒序。

### P3-2 仓库里有几处卫生问题

- `批量压缩解压.csproj.user` 被 Git 跟踪，内容是旧 WinForms 的 `批量压缩解压文件.cs` 引用；`.gitignore` 已忽略 `*.user`，但这个文件是早期提交进来的，应 `git rm --cached`（不删本地）。
- `schemas/ndjson-schema-v1.json` 的 `$id` 还是 `https://github.com/x/compress/...`，不是当前仓库地址。
- `macos/Info.plist` 的版本回退值还是 `0.6.5`；打包脚本会覆盖，但直接看文件或手工构建会误导。
- 根目录旧目录 `BatchCompress.Avalonia/` 只有本地 `bin`/`obj`，未跟踪，可清理本机，不影响仓库。
- README 的 CI 徽章仍指向云端 Actions；按你的决定它不是门禁，徽章容易让人误以为“云 CI 通过才算交付”。可保留但加一句“仅参考，本地验证为准”，或移除。

## 五、下一步开发建议（分批）

原则：**先修数据安全与安全边界，再修跨平台承诺，最后做验证链与文档治理**。每批独立提交、可单独回滚；改产品源码的批次各自递增 `0.0.1` 版本。

### 批次 30：运行中关窗与覆盖写入安全（P0，建议先做）

**目标**：任何用户中断都不留下“看似完成、实际损坏”的归档，也不留下孤儿进程和临时目录。

1. **关窗保护**
   - 在 `MainWindow_Closing` 检查 `IsOperating`；
   - 弹程序内确认框（不是浏览器/系统原生框），说明会取消当前任务；
   - 确认后调用 `Cancel`，等待 `OperationSession` 收尾（上限 10 秒）；
   - 超时才强制退出，并写崩溃日志；
   - 操作结束后再 `Dispose`，不要提前释放日志器；
   - 验收：长任务中关窗 → 取消 → 进程退出 → 无半成品、无附件暂存目录、无 `7zz`/`rar` 子进程；单元测试覆盖 `Closing` 取消分支。

2. **覆盖写入原子化**
   - 覆盖模式下先写临时输出（多卷写临时卷组），成功并校验后替换旧文件；
   - 失败时删除临时文件、保留旧归档；
   - 验收：假引擎写入一半后返回失败，旧归档字节不变；新临时文件被清理。

3. **目录大小计算防符号链接**
   - 抽 `DirectorySizeCalculator`，排除重解析点、忽略无权限目录、按目录收集错误；
   - 验收：符号链接环路测试在 1 秒内结束，统计不越界；无权限子目录只记一条错误，不中断。

**改动面**：`Views/MainWindow.axaml.cs`、`ViewModels/MainWindowViewModel*.cs`、`CompressionItemAdapter.cs`、新增 `DirectorySizeCalculator.cs` 与测试。
**风险**：关窗确认会改变用户习惯；覆盖原子化在多卷命名上要小心。两项都可用“先写临时、失败回滚”兜底。

### 批次 31：安全边界收口（P0/P1）

**目标**：不让程序执行不受信任目录里的二进制；让所有对外文本的密码兜底一致。

1. **移除当前目录 7-Zip 搜索**（P0-3）
   - 生产只查程序目录与系统路径；
   - 显式 `BATCHCOMPRESS_7ZZ_PATH` 或调试开关才允许自定义；
   - 测试：临时工作目录放伪造 `7zz`，断言不执行；显式路径可用。

2. **统一密码兜底**（P2-2）
   - 抽 `CredentialRedactor`，诊断包、结果报告、NDJSON 共用；
   - 保留“命令输出整条排除”的第一道保证；
   - 测试：引号整体、等号/冒号、普通路径 `-pictures` 三类。

3. **“随机密码”语义诚实化**（P1-1）
   - 五语言标签改成“按文件名生成密码”；
   - README/帮助说明“兼容旧版，不是密码学保护”；
   - 是否新增真正随机模式，见第六节。

4. **日志与诊断权限复核**（P2）
   - 在 Windows 上确认 `%LOCALAPPDATA%` 日志 ACL 是否只允许当前用户；

**改动面**：`SevenZipArchiveEngine.cs`、新增 `CredentialRedactor.cs`、`BatchReportService.cs`、`NdjsonOutputWriter.cs`、五份 JSON、README。
**风险**：移除当前目录搜索会影响开发时“仓库根目录直接运行”的便利，用显式环境变量补上即可。

## 六、需要你拍板的三件事

> 按你的要求，这里把现状、不改的后果、选项和推荐都写全，不用简称。

### 决定一：Windows 命令行怎么输出

**现在是什么情况**：Windows 产物是图形界面程序（`WinExe`），从命令提示符启动时没有控制台，帮助、进度、错误都看不到。现有测试只测测试工程，不测打包后的 exe，所以一直没暴露。

**不改会怎样**：Windows 用户无法用命令行批处理，也无法把输出重定向给脚本；这对“完整命令行入口”是硬伤。

**选项与代价**：

1. **拆成两个程序**：图形界面一个、命令行一个，共用同一套代码。
   - 优点：两边都干净，命令行输出、退出码、重定向都正常；
   - 代价：打包、图标、快捷方式、文档要区分两个文件，工作量最大。
2. **只保留普通控制台程序**：启动图形界面时用系统调用把控制台窗口隐藏。
   - 优点：改动较小，命令行天然可用；
   - 代价：从资源管理器双击时可能闪一下黑色窗口；需要 Windows 实测隐藏是否干净。
3. **保持图形程序 + 附加父控制台**：命令行模式下调用系统接口附加到启动它的控制台。
   - 优点：改动最小，不动打包结构；
   - 代价：只在“父进程有控制台”时有效；重定向到文件、计划任务、无控制台启动可能仍然拿不到输出，需要逐场景实测。

**我的推荐**：先做选项 2 的 Windows 试验（成本最低、命令行最可靠）；如果闪窗无法接受，再拆两个程序。选项 3 只作为过渡，不作为长期方案。

### 决定二：“随机密码”要不要变成真随机

**现在是什么情况**：界面叫“随机密码”，实际是按文件名加固定字符串做 MD5，得到固定密码；同一文件名永远得到同一密码。提示文字写的是“按文件名生成”，但主标签仍是“随机密码”。

**不改会怎样**：用户会以为归档有密码学保护；实际上拿到归档的人知道文件名就能算出密码。这不一定是漏洞（旧版兼容需要），但属于安全预期误导。

**选项与代价**：

1. **只改文案**：五语言标签改成“按文件名生成密码”，帮助和 README 说明“兼容旧版，不是密码学保护”。
   - 优点：零兼容风险，立刻消除误解；
   - 代价：没有真正提升保护强度。
2. **新增真随机模式**：用系统密码学随机数生成器生成足够长的密码，作为显式选项。
   - 优点：真正提升保护；
   - 代价：用户必须自己保存密码，否则无法恢复；需要新增“显示/复制/保存密码”的流程；默认值不能悄悄改，否则旧归档密码查询失效。
3. **直接改默认算法**：不推荐，会破坏历史密码兼容，也会让用户旧归档打不开。

**我的推荐**：先做选项 1；如果你确实需要真加密，再做选项 2 的显式模式，默认仍保持旧行为。

### 决定三：任务执行中关闭窗口怎么处理

**现在是什么情况**：点关闭就直接退出进程，正在跑的压缩/解压被硬中断，清理逻辑来不及执行。

**不改会怎样**：可能留下半个归档、临时目录、孤儿压缩进程；用户以为关了没事，实际磁盘上有残片。

**选项与代价**：

1. **阻止关闭并提示**：告诉用户“任务执行中，请先取消或等待完成”，不提供一键退出。
   - 优点：最安全；
   - 代价：用户想强退时会被挡住。
2. **确认后取消并等待清理**：弹程序内确认框，确认后取消任务，等清理完成再退出（推荐）。
   - 优点：既安全又给用户出口；
   - 代价：退出会慢几秒，需要处理“清理卡住”的超时。
3. **保持现在的强制退出**：只在日志里记一笔。
   - 优点：实现最简单；
   - 代价：数据残片风险仍在。

**我的推荐**：选项 2。超时（例如 10 秒）后提示“清理未完成，仍要退出吗”，再决定是否强制。
