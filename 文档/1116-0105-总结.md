## 四、逐项问题

### 【高 1】崩溃日志去重会吞掉最该留下的那次记录

**现在是什么情况**

崩溃日志服务（`Core/Services/CrashLogService.cs`）为了避免异常风暴刷爆磁盘，做了 2 秒去重：同一个错误在 2 秒内重复出现时，只写第一个文件，后面的只累加一个内部计数（`_suppressed`）。这个计数只有在**下一次出现不同错误**时，才会以 `suppressed=N` 的形式附写到那个新文件里。

**不改会怎样**

- 如果同一错误连续重复 100 次，然后进程退出，磁盘上只有 1 个文件，里面**没有任何「这个错误重复了 99 次」的信息**。诊断时无法判断是偶发还是持续故障。
- 更严重的是进程级兜底（.NET 里整个进程都没接住的异常，`AppDomain.UnhandledException`）也走同一套去重。它发生在进程即将终止的那一刻，如果 2 秒前刚记录过同签名异常，这次会**直接 `return`，一个文件都不写**。最该留下证据的那次反而丢了。
- `Program.cs` 里启动期致命异常、`HeadlessBatchRunner.cs` 里命令行致命异常，同样走非强制写入。

**根因**

去重判定与写入是同一个入口，没有区分「可去重的普通异常」和「必须落盘的致命异常」；被抑制的次数只存在内存里，没有周期性或在进程退出前落盘。

**建议**

1. 给写入增加一个「强制」通道，进程级兜底、启动期致命异常、命令行致命异常三处绕过 2 秒去重。
2. 被抑制的累计次数在下次写入时落盘；如果没有下次写入，至少追加一行到最近一次崩溃文件，或由进程退出钩子补写。
3. 补测试：连续重复后断言抑制次数确实出现在文件里；同签名的致命异常必须新写一个文件。

**测试缺口**：`Program.CrashLogTests.cs` 第 50–52 行只断言「2 秒内同签名只写一条」，没有断言抑制次数是否落盘，也没有覆盖强制写入。

### 【高 2】命令行 `--report` 在提前返回路径静默失效

**现在是什么情况**

命令行结果报告的写出，被放在批处理正常结束时（`HeadlessBatchRunner.cs` 第 213–229 行「try 块尾部」）。但同一个方法里有四条路径会在到达那里之前就 `return`：

1. 试运行（`--dry-run`，第 103–106 行）
2. 仅导出诊断包（`--export-diagnostics`，第 55–73 行）
3. 用户按 Ctrl+C 取消（返回退出码 130）
4. 批处理过程中抛异常（返回退出码 1）

这四条路径既不写报告，也不输出任何说明。

**实测证据**（最新构建，退出码均为 0 或正常）

```
场景：compress --input ... --format 7z --dry-run --report dryrun.csv --quiet
退出码=0
结果：报告未生成（用户指定了 --report 却拿不到文件）

对照：同上但去掉 --dry-run
Batch report: .../normal.csv (1 items)
退出码=0
结果：报告已生成
```

**不改会怎样**

用户最需要「已完成哪些、失败哪些」的场景恰恰是取消和失败，而这些场景恰恰拿不到文件；用户会以为功能坏了或数据丢了。试运行场景下退出码还是 0，看起来完全成功。

**建议**

1. 把报告写入移到统一收尾位置（`finally` 或一个所有返回路径都会经过的收尾方法），取消与异常路径也要写部分结果。
2. 试运行与诊断导出模式确实没有逐项数据时，至少往标准错误输出一句明确说明，不要静默。
3. 保持现有约定不变：报告写失败只告警，不改变批次退出码。
4. 补四条路径的测试或经验验证用例。

### 【中 3】结果报告未本地化，英文模式下中英混排

**现在是什么情况**

报告的表头、标题、结果词、汇总句、省略说明全部写死为中文（`BatchReportService.cs` 第 152–209 行）；命令行构造报告收集器时，操作类型也写死为「压缩 / 解压」（`HeadlessBatchRunner.cs` 第 47 行）。

**实测证据**（指定英文语言后导出的 CSV）

```
"序号","操作","来源","结果","说明","处理量(MB)","耗时(秒)"
"1","压缩","a.txt","成功","Success: a.txt","0.000","0.061"
```

表头、操作、状态是中文，消息内容却已经是英文，属于明显混排。对照同一版本的英文帮助文本是正常的英文：`--report <csv or md path> Export per-item results ...`。

**还有一个时序问题**：操作类型是在命令行运行器**构造时**求值的，而语言是在 `Program.cs` 第 87 行（构造之后）才设置的。就算把字面量换成词条，按现在的调用时机仍然会拿到默认中文。

**不改会怎样**

四种非中文语言的用户导出的报告都是中文骨架，交付给他人时观感不一致；后续加语言也容易漏。

**建议**

1. 报告文案统一走本地化词条（约 10 个新键：七个表头、标题、结果状态、汇总句、省略说明、两种操作名）。
2. 把操作类型的求值挪到报告写入之前、语言设置之后。
3. 扩展界面本地化扫描，或增加一条「报告输出语言」测试。

**关联缺口**：界面本地化扫描（`Program.LocalizationTests.cs` 第 166 行）只检查界面描述文件、`MainWindow` 代码隐藏和 `App` 代码隐藏，**完全不覆盖服务层目录**。所以这批成片的中文在现有门禁下不会被发现——这不是漏测，是扫描范围没跟上新服务。

### 【中 4】导出的 CSV 未防表格软件公式注入

**现在是什么情况**

CSV 单元格的转义只把双引号翻倍（`BatchReportService.cs` 第 242–246 行）。来源文件名和说明文字来自用户数据，完全可能以 `=`、`+`、`-`、`@` 开头，表格软件打开这类单元格会当成公式而不是文本。

**实测证据**

```
文件名：=1+1.txt
导出结果："1","压缩","=1+1.txt","成功","成功: =1+1.txt","0.000","0.042"
```

**不改会怎样**

用 Excel / WPS / LibreOffice 打开报告时，特殊文件名会触发公式求值；更激进的构造可以调用外部命令或读取本地数据。这是导出的报告文件被转发给他人时的风险，不是本机运行时风险。

**建议**

对以 `=`、`+`、`-`、`@`、制表符、回车开头的单元格前置单引号或做等价中和，并固定一条断言测试。项目已有「报告默认不含密码」的既定策略，这条属于同一类的输出安全。

### 【中 5】界面日志尾部可能停在缓冲里不显示

**现在是什么情况**

进度回调（`OperationSession.cs` 第 57–58 行）用的是 .NET 的 `Progress<T>`：它把回调**异步投递**到界面线程的消息队列，调用方不会等待回调执行完。批次结束时，`finally` 里只同步调用一次强制刷新（第 113 行）。

项目自己在执行管线的注释里已经写明「IProgress 可能异步投递回调，因此命令输出必须使用独立快照」——这个认知是有的，但没有应用到日志刷新的时机上。

**不改会怎样**

批次结束那一刻，消息队列里可能还排着没执行的进度回调。`ForceFlushLogs()` 先跑完，随后这些回调才把最后几行追加进缓冲；因为之后再没有追加、也没有第二次刷新，**这几行就一直停在内存里，界面上看不到**，直到下一次任务或用户清空日志。这正好是上一个批次（日志有界缓冲与强制刷新）想根除的问题。

**建议**

1. 在界面消息队列里再排一次低优先级的兜底刷新，确保所有在途回调执行完后再刷一次。
2. 或者让缓冲在「有未刷新内容且一段时间没有新追加」时自行做一次尾刷新。
3. 补一条模拟「追加后立即结束、之后仍有迟到回调」的测试。

> 附带说明：报告收集器也在同一个回调里，但导出报告是用户后续动作，通常不受影响；只有批次刚结束就立刻导出才可能少项。

### 【中 6】崩溃日志临时文件的权限窗口与残留

**现在是什么情况**

写崩溃日志时，先把内容写进一个 `.tmp` 临时文件，再改名成正式日志，最后才把权限收紧为仅本人可读写（`CrashLogService.cs` 第 171–178 行）。临时文件创建时是系统默认权限，通常同机其他用户可读。

**不改会怎样**

- 崩溃日志会包含完整堆栈，而项目既定的诊断策略是**保留归档命令原文、不做密码脱敏**，所以内容可能含明文密码。从写临时文件到改权限之间存在一个可读窗口。
- 如果进程恰好在这两步之间终止，会留下一个权限宽松的 `.tmp` 文件；而轮转清理只匹配 `*.log`（第 197 行），这个 `.tmp` **永远不会被清理**。

**建议**

临时文件一创建就先收紧权限再写内容；轮转清理把陈旧 `.tmp` 一并纳入，或在启动时清理。补一条断言临时文件权限的测试。

### 【低 7】日志缓冲误删中间空行（实测确认，与注释矛盾）

**现在是什么情况**

日志缓冲按行拆分时，用「当前空段和最后一段是不是同一个对象引用」来判断末尾空段（`LogBuffer.cs` 第 65 行）。实测 .NET 10：拆分产生的所有空段都是同一个 `string.Empty` 对象，因此只要文本末尾带换行，**中间的所有空行也会被当成末尾空段跳过**。而日志追加几乎总是 `消息 + "\n"`，末尾必然带换行，所以这个分支在实际运行里总是触发。

**实测证据**（临时探针，验证后已删除）

```
输入: a\n\nb\n
  分段数=4, 末尾段长度=0, 空段索引=[1,3]
  按引用判定会被跳过的索引=[1,3]  <-- 期望只有最后一个
  是否误跳过中间空行: 是（缺陷成立）
```

代码注释写的是「中间的空行保留（用于分隔区块）」，实际不成立。

**不改会怎样**

只影响日志可读性（区块之间的空行消失），不影响压缩解压结果。

**建议**

改用索引判断（当前是不是最后一个分段）；测试第 2 项只覆盖了「多行且没有中间空行」，需补一条带中间空行的用例。

> 顺带一提：测试里写 `flushIntervalMs: 0` 想表达「立即刷新」，但构造函数会把 0 兜底成 200 毫秒。测试用无条件刷新绕过了这个差异，所以没暴露，建议把测试意图写清楚。

### 【低 8】界面线程异常被无条件吞掉

`App.axaml.cs` 第 42–47 行把所有界面线程异常记录后一律标记为「已处理」，应用继续运行。好处是窗口不会因为一次异常就退出，代价是如果异常发生在窗口还没构建完、或某个渲染循环里反复触发，用户看到的是一个空白或半初始化的窗口，**界面上没有任何提示**，只有日志目录里的文件。

叠加【高 1】的去重问题，反复触发的异常在 2 秒后只留下 1 条记录且抑制次数丢失，排查线索会非常少。

建议：至少对启动期异常、以及连续多次同类异常给出一次可见提示或不再吞掉，并与强制写入联动。

### 【低 9】界面导出文件名只精确到秒

`MainWindowViewModel.BatchReport.cs` 第 33–34 行用 `yyyyMMdd-HHmmss` 命名，同一秒内点两次「导出本次结果」，第二份会覆盖第一份。建议加毫秒或短序号。

### 【低 10】窗口状态服务自身不校验宽高（已核对，当前安全）

新服务 `WindowStateService.Load()` 会把 JSON 里的宽高原样返回，不排除 0、负数或非数值。但对照重构前版本并核对当前界面层后确认：`Views/MainWindow.axaml.cs` 第 126 行仍保留尺寸有效性校验，路径也与原实现完全一致（用户已有的窗口位置不会丢）。**这不是功能退化**，只是服务层单独被其它调用方使用时的契约不完备。可在服务层补校验与单测，优先级最低。

## 七、建议修复顺序

**建议先修这五项**（风险与收益最匹配，且互不冲突）：
